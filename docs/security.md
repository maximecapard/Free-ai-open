# Security design

## Security principles

- Privacy-first.
- Secure-by-default.
- Observable-by-design.
- Minimal server data.
- Explicit user control.

## Required protections

- Strict CSP. Not yet enforced (see `netlify.toml`); when added, it must allow-list or hash the small inline theme-init script in the root layout (a static, non-user-controlled snippet that reads a `localStorage` preference and sets `<html data-theme>` before hydration to avoid a theme flash), rather than broadly allowing inline scripts.
- No `eval`.
- No unnecessary remote scripts.
- Worker isolation for inference.
- Telemetry payload validation.
- Privacy redaction client-side and server-side.
- Forbidden telemetry fields rejected.
- Rate limiting on telemetry endpoint.
- Model registry validation.
- Model manifests with source, license, hash when possible.
- Dependency review.

## Threats to document

- XSS.
- Compromised model manifest.
- Compromised CDN/model source.
- Sensitive data in logs.
- Prompt injection in documents.
- WebGPU crash/device lost.
- Excessive fingerprinting.
- Storage exhaustion.
- Local conversation storage leakage.
- Malicious dependency.

## Local conversation storage

Conversations are sensitive local data. The conversation store must:

- stay browser-local;
- avoid `fetch`, `sendBeacon`, Supabase, Google Drive, and server endpoints;
- avoid local technical logs for message content;
- enforce limits on conversation count, message count, and message size;
- keep schema version metadata for future migrations;
- exclude conversation content from diagnostic reports.

Sprint 5.1 test coverage includes the real IndexedDB store through `fake-indexeddb`, no-IndexedDB memory fallback, active conversation ID pointer behavior, local-log rejection of conversation content fields, diagnostic-report exclusion of conversation-shaped input, and network isolation for conversation-store operations.

The store's optional per-conversation `task` field is a plain string passed through unvalidated at the storage layer (the app layer, not the store, validates/narrows it against the `TaskCategory` catalog); it is never prompt or response content and carries no additional privacy risk beyond the existing title field.

## Local conversation export/import

Conversation export files are sensitive local data because they can contain prompts and model responses. The export/import package must:

- stay local-only;
- avoid `fetch`, `sendBeacon`, Supabase, Google Drive, cloud storage, and server endpoints;
- reject unsupported formats and versions;
- reject invalid roles, invalid dates, oversized payloads, and unexpected fields;
- reject a `task` field that isn't a bounded string, while still accepting a file where `task` is absent entirely (older exports);
- assign fresh conversation IDs during import so existing conversations are not silently overwritten;
- keep exported/imported conversation content out of local technical logs and diagnostic reports.

The current export format is unencrypted JSON. Users should treat exported files as private data until encrypted export is implemented.

The `/chat` export/import UI enforces this at the app layer too: it calls only `conversation-export`/`conversation-store` public functions, never `fetch`, `sendBeacon`, a server endpoint, `logEvent`, local technical logs, or diagnostic reports, and it always imports conversations under fresh IDs rather than overwriting existing ones.

## Generation safety

The WebLLM runtime includes alpha safeguards for unstable model output:

- bounded `max_tokens` for generation requests;
- a first-token-timeout/stall-timeout generation watchdog that detects only absence of progress, never total duration alone (`packages/ai-runtime/src/generationWatchdog.ts` — see `docs/architecture.md`'s "Generation timeout and stall watchdog"), plus a wholly separate, much larger emergency duration cap (`generation_exceeded_safety_limit`) for a truly runaway generation;
- output character limits;
- detection for long unbroken sequences, repeated characters, and repeated punctuation/symbol blocks;
- technical-only events such as `inference.degenerate-output`, `inference.first-token-timeout`, `inference.stall-timeout`, and `inference.generation-safety-limit`.

When Stop, degenerate-output detection, or a first-token timeout (no output ever produced) fires, partial assistant output is not stored as a completed assistant message. A genuine stall or safety-limit interruption that had already produced visible assistant text is the one exception: that partial reply is saved with durable `status: "incomplete"` provenance, preserved through local reload/export/import, and rendered as incomplete rather than normal completed output. This content remains solely in the conversation store/export path; technical events, local logs, and diagnostic reports contain technical metadata only.

The chat transcript renderer may batch generated text briefly in memory before updating React state. This is a UI-only performance buffer, not a logging or diagnostic path, and must not be connected to telemetry, local technical logs, diagnostic reports, or server endpoints.

## Markdown rendering

Added in `v0.7.1-alpha` (`apps/web/app/_components/MessageContent.tsx`, `CodeBlock.tsx`; see `docs/architecture.md`'s "Message rendering"). Assistant Markdown renders as structured content; the threat model is untrusted, model-generated text that must never gain script execution, arbitrary HTML, or an unconsented network request.

- **No raw HTML.** `react-markdown` is used without the `rehype-raw`/`rehype-sanitize` plugins, so raw HTML embedded in the Markdown source — a `<script>` tag, an `onerror=`/`onclick=` attribute, a `<style>` block, an `<iframe>` — is dropped while converting the Markdown AST to the render tree; it is never parsed into real DOM nodes. `dangerouslySetInnerHTML` is not used anywhere for model output. This is verified by tests, not only documented: `MessageContent.test.tsx` feeds `<script>`/`onerror=`/`<style>`/`onclick=` payloads through the renderer and asserts none of that markup appears in the rendered output.
- **No arbitrary code execution.** Fenced code blocks are always displayed as plain, unhighlighted monospace text. Nothing in the renderer or the copy action ever executes, evaluates, previews, or downloads code — copying only ever calls the Clipboard API's `writeText` with the exact source text.
- **URL allowlist.** `apps/web/app/_lib/markdownLinkSafety.ts`'s `sanitizeMarkdownUrl()` is the single choke point for every link and image URL (wired through react-markdown's `urlTransform` prop and the `a`/`img` component overrides). Only `http:`, `https:`, and `mailto:` absolute URLs pass; `javascript:`, `data:`, `vbscript:`, `file:`, protocol-relative (`//host`), and bare relative URLs all resolve to an empty target, rendered as plain non-clickable text rather than a dead or dangerous anchor. External links that do pass always render with `target="_blank" rel="noopener noreferrer nofollow"`.
- **No implicit network requests.** Markdown images are intentionally never rendered as `<img>` — a real `<img src="...">` makes the browser fetch that URL the instant it renders, with no user action and no consent, which would let model output silently phone home to an attacker-chosen or tracking URL. The image's alt text/URL is shown as safe plain text (or a sanitized link, going through the same URL allowlist) instead.
- **Persistence is unaffected.** Parsing happens only in the rendering layer at display time; the message content written to `@free-ai-open/conversation-store` and read back through `@free-ai-open/conversation-export` is always the original plain Markdown source string, verified unchanged by `conversationMessages.test.ts`.
- **No content in logs.** The renderer and the copy button never call `logEvent`, `addLocalLog`, or `console.*` — confirmed by a source-scanning test (`MessageContent.test.tsx`) in addition to code review, so a future change that accidentally adds a logging call to these files fails a test rather than shipping silently.

## Reasoning disclosure

Added in `v0.7.1-alpha` (`apps/web/app/_components/ReasoningDisclosure.tsx`, `apps/web/app/_lib/reasoningSegmentation.ts`; see `docs/architecture.md`'s "Reasoning output and finish reason" and "Reasoning disclosure and Continue"). A Qwen3-style `<think>...</think>` block is untrusted model output like any other assistant text, so it carries the same threat model as "Markdown rendering" above, plus its own presentation- and persistence-specific guarantees.

- **Same rendering security guarantees as the final answer.** Reasoning content is rendered through the exact same `MessageContent` component and therefore the exact same `react-markdown`-without-`rehype-raw`, URL-allowlist, and no-`<img>` protections described above — there is no separate, less-audited rendering path for reasoning text.
- **Raw `<think>` markup is never shown.** `reasoningSegmentation.ts` strips the tags themselves out of what reaches the renderer; the disclosure panel only ever receives the text between them (or nothing, if no `<think>` tag is present at all).
- **No content in logs.** `ReasoningDisclosure.tsx` and `reasoningSegmentation.ts` never call `logEvent`, `addLocalLog`, or `console.*` — confirmed by a source-scanning test (`ReasoningDisclosure.test.tsx`), the same pattern as `MessageContent.test.tsx` above, so a future change that accidentally adds a logging call to either file fails a test rather than shipping silently.
- **The Continue action's composed prompt is never persisted.** `continuationPrompt.ts`'s `buildContinuationPrompt()` restates the original request and the partial reply, with a "do not repeat" instruction, as a plain string sent to `runtime.generate()`. That composed string is a model input, not conversation content: it is never written to `@free-ai-open/conversation-store`, never exported, and never logged. Only the model's own newly streamed output — appended to the existing assistant message — is persisted, through the same `updateMessageContent()`/`addMessage()` paths already covered by "Generation safety" below.
- **The length-specific interrupted notice is a durable, technical-only fact.** Whether a generation hit `finish_reason: "length"` (or `"unsupported_tool_call"`/a watchdog stall/safety-limit/`"unknown_terminal"`) is persisted as `ConversationMessage.incompleteReason` (`@free-ai-open/conversation-store`) — a bounded, allowlisted enum value, never response content — and round-trips through local export/import unchanged. It is still never written to local technical logs or diagnostic reports (same guarantee as before; only where the value lives changed, from an in-memory flag to a durable field). A message from before this field existed (`incompleteReason` absent) correctly falls back to the generic interrupted notice, since its original cause genuinely cannot be known after the fact.
- **The generation/continuation pipeline itself never logs content.** `AppRuntimeProvider.tsx`'s generation accumulator (`priorContent`/`generatedDelta`/`mergedContent`), `apps/web/app/_lib/continuationMerge.ts`'s overlap-deduplication, `apps/web/app/_lib/continuationExecution.ts`/`watchdogRecovery.ts` (the Continue-attempt and watchdog-rollback orchestration extracted from `AppRuntimeProvider.tsx`), and `packages/model-router/src/contextBudget.ts`/`apps/web/app/_lib/generationBudget.ts`'s token-budget estimator never call `logEvent`, `addLocalLog`, or `console.*`, and never perform a network call of any kind — confirmed by a source-scanning test (`generationPipelinePrivacy.test.ts`) that also checks no logging call anywhere in the pipeline references any of these content-bearing variables by name, not only by omission.

## Persistent runtime ownership

The WebLLM worker/runtime is owned by a root-level client provider, not by the `/chat` route component. This prevents route-view unmount from becoming a security-sensitive implicit teardown path: navigating to Settings or Debug must not cancel generation, unload the model, or terminate the worker by itself.

Allowed runtime disposal/replacement triggers are:

- application-root teardown;
- explicit Reload model;
- recovery after a stuck/interrupted worker;
- a validated future performance/model transition that actually requires replacement.

Route-view unmount and hidden-tab visibility changes are not disposal triggers. Browsers may throttle hidden tabs, but the app must not intentionally unload the model only because visibility changed.

Provider state may include runtime status, model/backend metadata, current conversation ID, current generation ID, and in-memory transcript UI state. None of that may be connected to local technical logs, diagnostic reports, telemetry, server storage, Supabase, Google Drive, or other network paths in a way that exposes prompt, response, document, or conversation content.

## Cancellation recovery

After a Stop request, the interrupted runtime must not be trusted as ready for the next generation merely because the stream returned an abort confirmation. The app now treats the old worker as unsafe after cancellation, enters `recovering`, tears down the old worker using bounded termination, creates a replacement runtime, and returns to `ready` only after the model reload succeeds.

Recovery events are allowlisted technical events only:

- `runtime.recovery.started`
- `runtime.recovery.completed`
- `runtime.recovery.failed`

These events may include runtime status and technical error codes, but must not include prompts, responses, documents, conversations, message arrays, hidden language instructions, local file paths, API keys, or tokens.

## Device capability profiling

`@free-ai-open/device-profiler` mitigates the "excessive fingerprinting" threat by construction:

- every persisted signal is a coarse, bounded category (`formFactor`, `architectureClass`, `memoryClass`, `cpuConcurrencyClass`, `capabilityClass`, GPU vendor/architecture/description classes, feature classes, and selected limit buckets), never a raw sensor reading, a raw user-agent string, or a combination precise enough to uniquely identify a device;
- architecture detection uses the Client Hints high-entropy API only when available and only reads the single `architecture` hint, never broader high-entropy fingerprinting hints;
- WebGPU adapter info may be read ephemerally to derive coarse GPU classes, but raw GPU names, device IDs, vendor/device strings, driver strings, exact high-entropy limits, exact VRAM, and fingerprint hashes must not be stored, logged, exported, or transmitted;
- fallback/software adapters are capped conservatively, and browser-reported experimental memory heaps are optional low-confidence buckets, not authoritative VRAM;
- the profiler never calls `fetch`, `sendBeacon`, or any server endpoint — profiling stays entirely local and synchronous with the existing onboarding/`/debug` display paths;
- an optional `measuredPerformance` input (tokens/sec, load/first-token time, recent failure count) is locally supplied only, never derived from remote data, and is not populated with real data by any current caller.

## v0.7.0-alpha adaptive router inputs and pure core (Phases 0-6)

Contracts and local persistence shapes exist, Phase 1A implements the static capability detector, Phase 1B adds a strict verified model registry, Phase 2 adds the local benchmark, Phase 3 implements the pure router core, and Phase 4 applies decisions to the runtime:

- Hard compatibility gates must run before any scoring (an unverified model, an unavailable backend, a missing required WebGPU feature/limit, clearly insufficient memory, a known incompatibility, or repeated recent OOM/device-loss/stall failures excludes a model outright).
- RAM alone must never determine model selection; exact VRAM must remain optional and never required.
- An experimental browser-reported GPU memory heap size is bonus data only, never authoritative.
- The adaptive core is deterministic for the same normalized input, registry version, and clock. It returns stable technical codes and candidate/rejection details rather than making a silent choice; later UI translation remains separate.
- Manual model override is allowed only for eligible models unless an explicitly designed advanced/unsafe override is added later.
- `StaticCapabilityProfile`'s `gpu` shape exposes only coarse classes and bounded feature/limit maps; there is no field for a raw adapter string. The browser store, diagnostic builder, and pure router each rebuild strict allowlisted shapes, so a type-cast caller cannot preserve unknown/private GPU keys or strings by bypassing one boundary.
- `LocalBenchmarkResult`/`ModelPerformanceObservation` must stay technical-only (timings, status/outcome codes, confidence) — never prompt, response, or conversation content — matching the existing local-log/diagnostic-report allowlist discipline elsewhere in this document.
- The three new local stores (`apps/web/app/_lib/capabilityProfileStore.ts`, `benchmarkResultStore.ts`, `modelObservationStore.ts`) must stay `fetch`/`sendBeacon`-free, matching every other local-only store in this codebase.
- Phase 2 runs its deterministic WebGPU workload in a dedicated client Worker with a hard timeout, cancellation/background-tab termination, validated output, reduced non-desktop workloads, and `finally`-based buffer/device cleanup. It never reuses or disposes the WebLLM runtime device.
- No new inter-package dependency edge was introduced while adding these contracts; `apps/web/app/_lib/packageDependencyBoundaries.test.ts` asserts `@free-ai-open/types` stays dependency-free and that `model-router`/`ai-runtime`/`model-registry`/`device-profiler` do not form a cycle, so a later phase that wires real logic gets an early test failure if it accidentally creates one.
- Model Registry v2 rejects unknown fields, unsafe URL schemes, duplicate IDs, unknown fallbacks, cycles, and incomplete verification metadata. Only fully verified records enter automatic routing.
- Registry production code is static and network-free. Its WebLLM dependency is test-only, used to compare exact model IDs, artifact URLs, model libraries, required features, and memory metadata against the installed prebuilt configuration; runtime WebLLM stays client-only.
- Phase 3 validates the whole registry before routing, applies hard gates before scoring, rejects repeated recent OOM/device loss, ignores user cancellations as failures, filters stale observations, bounds fallback attempts, and never allows manual selection to bypass a definite incompatibility. The core imports no browser API and performs no persistence, logging, telemetry, runtime loading, or network operation.

## v0.7.0-alpha Phase 4 (runtime integration) security notes

- A model switch is resolved through `apps/web/app/_lib/modelSwitchPolicy.ts`'s `resolveModelSwitch()` before any worker/model change: it is a hard no-op if the runtime is busy (`loading_model`, `generating`, `cancelling`, or `recovering`), so a routing moment landing mid-generation or mid-load can never interrupt it or start a second concurrent load — the next safe routing moment retries instead.
- A model that is neither cached nor the pre-disclosed compatibility default always requires explicit user confirmation (`ModelDownloadConsent`) before any download starts, including the very first automatic selection — this applies even when the router's confidence is high. The default's friendly name and approximate size are disclosed during first-run setup. Fallback candidates are filtered to cached, explicitly approved, or pre-disclosed models; declined and failed upgrades are suppressed for the current session so consent and load failures cannot loop. Cache status comes from the real Cache Storage API (`isModelCached()` in `ai-runtime`, defaulting to "not cached" — the safer direction — on any lookup failure), never inferred from registry metadata.
- `RouterDecision.selectedModelId`/`fallbackModelIds` and stored `ModelPerformanceObservation.modelId` are registry IDs; `InferenceRuntime.loadModel()`/`RuntimeState.modelId` are WebLLM model IDs. Every call site that bridges them goes through `routingOrchestration.ts`'s `buildLoadCandidatesFromDecision()`/`registryIdForWebllmModelId()` rather than ad hoc string handling, so an observation can never be silently recorded, or a switch silently resolved, against the wrong ID space.
- A model swap reuses the existing safe worker-teardown path: `runtimeLifecyclePolicy.ts`'s new `model_replacement` disposal trigger goes through the same `disposeCurrent`-then-`ensureRuntime` sequence as `explicit_reload`/`performance_replacement`/`recovery`, so a switch can never leave two workers alive at once.
- `attemptModelLoadWithFallback()` walks a candidate list already bounded by the router's own `maxFallbacks`, deduplicates candidates defensively, and records one observation per attempt — it cannot retry the same model or loop unbounded even if called with a malformed decision.
- `RouterDecision.recommendedContextTokens` is passed only as a bounded WebLLM engine context-window option and capped by verified registry presets. `recommendedMaxOutputTokens` can only reduce the independent global generation-safety limit.
- No cloud model profiling was added: capability, benchmark, and observation data used for routing are read from local storage only; nothing about device capability or model performance is sent to a server as part of this integration.

## v0.7.0-alpha Phase 5 (router UI) security notes

- Manual model selection does not bypass the download-consent flow: `setManualModel()` still resolves through the same `resolveModelSwitch()` gate as automatic routing, so a manually chosen, non-cached, non-default model still requires explicit confirmation before downloading, and a manual pick still cannot bypass the router's hard eligibility gates (a manually requested but ineligible model produces a warning and an automatic fallback, never a forced load).
- `apps/web/app/_components/ManualModelPicker.tsx` disables every manual model while capability-backed routing is pending, then disables any model the latest `RouterDecision` rejected. It uses the router's own `rejectedModels` output rather than a separate UI-layer eligibility re-implementation, so the disabled state cannot drift from what the router would actually reject.
- The manual model picker's per-model card structures the selectable button and the technical-details `<details>` disclosure as siblings rather than nesting the disclosure inside the button, avoiding invalid interactive-in-interactive markup that could produce inconsistent hydration/click behavior across browsers.
- The new local manual-selection preference contains only a mode flag and a public registry model ID — no conversation content, no device fingerprint — and follows the same schema-versioned, `try`/`catch`-guarded `localStorage` convention as every other local preference store in this codebase.

## Runtime language instruction

The selected UI locale is converted to a hidden runtime-only system instruction before local inference. This instruction is allowed to enter the local WebLLM message list, but it must not be persisted in conversation history, exported in conversation backups, included in diagnostics, or written to local technical logs. Language adherence remains best effort and depends on the selected model.

## v0.8.0-alpha local model benchmarking (Phase 0: contracts and architecture; Phase 1: runtime-backed metrics; Phase 2: benchmark core service)

Phase 0 defined the local data contract and persistence layer (`@free-ai-open/types`' `ModelBenchmarkResult`, the `@free-ai-open/model-benchmark` package); Phase 1 let `@free-ai-open/ai-runtime` capture real usage per generation (see its own bullet below); Phase 2 adds a bounded, cancellable benchmark runner core service in `@free-ai-open/model-benchmark` (`createModelBenchmarkRunner()`) together with the generic runtime-safety hardening it required (see the runtime ownership and isolation bullets below). The runner exists only as library code: `apps/web` has no runner instance, no production target/environment/eligibility/recovery adapters, and no benchmarks page, so none of it is reachable by a user today. The requirements below are enforced and tested at the core-service level; the app-level composition (and its own security review) is Phase 3 work.

- `ModelBenchmarkResult` has no field capable of holding prompt text or generated response text; `@free-ai-open/model-benchmark`'s `sanitizeModelBenchmarkResult()` rebuilds an exact allowlisted shape from scratch on every write and read, the same discipline `StaticCapabilityProfile`/`LocalBenchmarkResult`/`ModelPerformanceObservation` already follow — a malformed, corrupted, or unsupported-schema-version record is dropped entirely rather than partially trusted, coerced, or thrown on. Every storage backend (`indexed-db-store.ts`/`memory-store.ts`) independently re-runs this same sanitizer before its own write, as defense in depth, and neither backend is exported from the package's public index — `ModelBenchmarkStoreClient` is the only way anything outside the package can persist or read a result, so there is no reachable path that bypasses validation.
- Deliberately STRICTER than `apps/web/app/_lib/modelObservationStore.ts`'s own per-field-drop leniency: a benchmark result with any single impossible value (a negative or non-finite timing, an unknown outcome/stage/preset, a top-level/nested `modelId` mismatch) is rejected as a whole record, since a deliberate, infrequent, higher-stakes measurement containing one impossible value calls the entire run's integrity into question.
- `generatedTokenCount`/`overallCompletionTokensPerSecond` are only ever populated, and only ever trusted on read, when `tokenCountConfidence` is `"exact"` — a character-length-derived rate must never be accepted as authoritative, matching the existing `promptTokensPerSecond`/`generationTokensPerSecond` rule for real chat observations. When `"exact"`, the count must additionally be a non-negative integer, the duration strictly positive, and the claimed rate numerically consistent with count/duration within a small explicit tolerance — a plausible-looking but fabricated rate is rejected exactly like any other impossible value, not merely trusted because the record's shape matched. (This field was named `generationTokensPerSecond` in the original Phase 0 draft; renamed during Phase 2 for the same decode-only-ambiguity reason Phase 1's identically-shaped `ai-runtime` field was corrected — see docs/DEVLOG.md.)
- `capabilityProfileKey` is validated against the exact same low-entropy, four-segment grammar `buildCapabilityProfileKey()` produces (form factor / capability class / WebGPU availability / adapter kind, each from its own small allowlist), not merely a bounded-length string — an arbitrary high-entropy value, a UUID, or an exact GPU adapter description can never pass, closing a fingerprinting-key gap a length check alone would leave open.
- `@free-ai-open/model-benchmark` depended only on `@free-ai-open/types` through Phase 0/1; Phase 2 (see its own bullet below) adds exactly one new edge, to `@free-ai-open/ai-runtime`, for the runner's own orchestration — no edge touches `model-router` or `model-registry`, and `ai-runtime` has no edge back. `apps/web/app/_lib/packageDependencyBoundaries.test.ts` asserts this directly (depends on exactly `types`+`ai-runtime`, no dependency on `model-router`/`model-registry`, `ai-runtime` does not depend back, no cycle) alongside its existing v0.7 router/runtime/registry coverage.
- Phase 2's core runner is not app-composed yet. Its generic `ai-runtime` operation lease is already used by chat generation and app model load/reload/switch paths, so load/generate requires shared ownership rather than a racy status snapshot. Phase 3 must provide the production benchmark adapters/finalization and UI without weakening that lease or the existing download-consent policy.
- `isModelBenchmarkResultCompatible()`/`isModelBenchmarkResultUsable()` require an exact match on this package's own current `benchmarkVersion`, registry version, WebLLM version, coarse capability-profile key, AND browser family before a stored result is treated as usable evidence for anything — a partial match is never accepted, so a future router-integration phase cannot be misled by a result measured against a since-changed contract version, registry entry, runtime version, or browser engine. `expiresAt` is validated as an exact `createdAt + 30-day-TTL` formula on write (`calculateModelBenchmarkExpiry()`), so a forged or corrupted far-future expiry can never extend a result's usable lifetime.
- The IndexedDB backend inserts a new result and enforces the history cap in one atomic readwrite transaction, resolving only on `transaction.oncomplete` (never merely the last request's `onsuccess`) and rejecting on `onabort`/`onerror` — there is no window where a write succeeded but cap enforcement did not, or vice versa.
- No new `fetch`/`sendBeacon`/network call exists anywhere in `@free-ai-open/model-benchmark` — matching every other local-only store in this codebase.
- **Phase 1's runtime usage capture (`@free-ai-open/ai-runtime`).** Verified against the actually-installed `@mlc-ai/web-llm` 0.2.84 API before implementation (never assumed from memory or generic docs — see `runtime.ts`'s own top-of-file note). `buildGenerationTokenUsage()` treats WebLLM's raw usage payload as untrusted input: `completion_tokens`/`prompt_tokens`/`total_tokens` must each be a finite non-negative integer and `total_tokens` must equal their sum, or the whole measurement degrades to `tokenCountConfidence: "unavailable"` rather than persisting a partially-valid value. The one derived rate, `overallCompletionTokensPerSecond`, is computed from `ai-runtime`'s own measured FULL inference wall-clock duration (never from WebLLM's self-reported `usage.extra.*` timings), so a rate can never be asserted without the measurement that makes it verifiable — and its name is deliberately explicit that the denominator spans the whole call (worker overhead, prefill, TTFT, decode, stream delivery, and the usage-trailer wait), never a decode-only surrogate. No prompt/prefill-throughput field exists anywhere in this contract: `promptTokens / timeToFirstTokenMs` is not exact prefill throughput (TTFT is not a prefill-time measurement — it includes request scheduling and first-token sampling too), so it is never exposed as one, not even nullable. No new dependency was added to reach this: the new metrics types are package-local, not imported from `@free-ai-open/types` or `@free-ai-open/model-benchmark`. No new `fetch`/`sendBeacon`/`WebSocket`/`XMLHttpRequest` call exists anywhere in the changed source, and `@free-ai-open/local-logs`' extended schema carries only timings/counts/confidence — never prompt, response, or any generated content, and never a prompt-throughput field either.
- **Phase 2 trust adapters are privileged but fallible.** Public `start()` accepts only `{modelId}`. Resolver/environment output is immediately sanitized, the resolved id must equal the requested id, and eligibility output is runtime-validated before cache/load. Malformed WebLLM ids, provenance/version/quantization/verification fields, browser families, low-entropy capability keys, modes, and app versions fail closed with no runtime operation. Production adapter implementations remain Phase 3 work.
- **Consent bound to a specific run and model fingerprint, single-use, never cache-gated.** An initial draft treated `isModelCached()` as a security boundary (skip consent for a "cached" model) -- a time-of-check/time-of-use gap, since a partial/corrupted/stale cache entry can still cause a real network fetch despite an earlier "cached" result. The corrected design requires consent for ANY load (cache status is informational only, persisted for evidence but never a gate), issues an opaque `consentRequestId` scoped to the current run, and `confirmConsent()` re-resolves and re-validates the trusted target/environment/eligibility completely fresh before proceeding -- a stale, forged, cross-run, or already-used consent id is rejected (`invalid_consent`/`consent_stale`), and a model whose registry fingerprint changed since consent was requested can never have that earlier consent silently reused against the new one.
- **Per-attempt isolation prevents a stale async result from mutating a later/concurrent run's visible state.** An initial draft's second `start()`-while-busy rejection called the SAME state setter as normal transitions, which would have overwritten the ACTIVE run's own visible state with a bogus "failed" status. The corrected design gives every attempt its own `RunContext` object; a second `start()`/`confirmConsent()` call while one is active returns a rejection describing only its OWN outcome without ever touching the active run's state, and every internal async step checks it is still the current run (by object-reference equality, not merely a numeric epoch convention) before acting.
- **Runner policy and unknown termination are never reported as model instability.** `benchmark_timeout`, `load_timeout`, and `terminal_unknown` are neutral. Silent iterator completion and generic unknown runtime errors map to `terminal_unknown`; only the explicit `generation_stalled` runtime signal produces negative `stalled` evidence.
- **Metrics are never fabricated.** `firstTokenTimeMs`/`generationDurationMs`/token counts/rate are read ONLY from a real Phase-1 `GenerationRuntimeMetrics` object attached to an actual `"done"` chunk; when no such object exists (an error chunk, or the hard-teardown give-up path), the measurement is honestly absent rather than reconstructed from the runner's own wall-clock tracking. `validation.ts`'s `sanitizeModelBenchmarkResult()` was corrected to make this representable (a one-directional `firstTokenTimeMs` legality check) rather than forcing a choice between a fabricated value and rejecting an otherwise-valid record.
- **Evidence validity does not hide runtime recovery failure, and readiness is never mistaken for isolation.** The required abort-aware recovery adapter runs under the benchmark lease and reports TWO independent facts, `{isolated, ready}`. `isolated: true` means the old runtime work is quiescent or physically isolated; only that decides whether ownership is released. `{isolated: true, ready: false}` releases the lease and ends as `failed/runtime_recovery_failed`; `isolated: false`, a rejection, a malformed/legacy result (a boolean or `null` fails closed to unproven), a timeout, or an adapter that ignores its abort signal quarantines the lease and ends as `failed/runtime_isolation_failed`. Recovery is mandatory after any abandoned load or generator regardless of the runtime's reported status. `ready: true` is accepted only while the runtime really reports status `"ready"` -- `"idle"` is not readiness and is never silently normalized to it; a claim the runtime contradicts fails closed as `runtime_recovery_failed`. Valid evidence is still persisted when possible and returned as `persistedResult`; `completed` therefore means persistence succeeded and a usable runtime remains, never merely that evidence exists.
- **Exact requested output, not a mismatched ceiling.** An initial draft persisted `requestedOutputTokens: 128` while actually requesting 256 tokens from the runtime -- false benchmark metadata. The corrected preset uses one `outputTokens` value for both, verified directly against the runtime call in `runner.test.ts`.
- **Injected failures are contained, and no wait on a dependency is unbounded.** One deadline is created per contiguous automated burst. The thunk-based wrapper checks remaining budget before invocation, catches synchronous throws and rejected promises, clears its timers, and maps failure into deterministic state. After a timeout the runner aborts the operation and waits at most a fixed grace for it to confirm it stopped; an operation that ignores its `AbortSignal` is ABANDONED and the run fails closed instead of waiting forever -- an abandoned runtime recovery quarantines the runtime lease, whereas an abandoned storage write never does (storage failures are separate from runtime safety). Human consent wait is excluded; `confirmConsent()` starts one new burst deadline reused through revalidation, lease, runtime work, recovery, and persistence. The guaranteed ceiling is the work budget plus the fixed isolation windows (`maxAutomatedBurstMs()`), not a hard 220 s wall.
- Every result still passes through `sanitizeModelBenchmarkResult()` and `ModelBenchmarkStoreClient.recordResult()`. Writes accept an `AbortSignal` that the IndexedDB adapter honors from `open()` onward: a pre-aborted signal never opens the database, an abort during a pending open rejects promptly and makes the late open inert (connection closed, no transaction, upgrade aborted), an abort that arrives while an upgrade is already in progress aborts that versionchange transaction at once (the schema and version change roll back), and once a transaction exists the abort/error terminal event is awaited. A store that honors its signal cannot commit after the run moved on. The runner accepts only a trusted, package-created store client (see the persistence trust boundary below), so a store that ignores its signal is not an expected input; if one nevertheless fails to settle past the bounded grace the run ends as `persistence_isolation_failed` and new benchmark runs wait (`persistence_unsettled`) until it settles. The runtime lease is NOT quarantined for it: the lease was released before persistence began, and a storage write cannot affect the runtime. Terminal state never contains prompt/response/raw chunks; only `completed.result` or `failed.persistedResult` carries the sanitized technical result. No benchmark network/upload path or telemetry was added.
- **Persistence trust boundary.** The runner's no-late-write guarantee is a property of specific storage implementations, not of a TypeScript shape, so only stores this package created are trusted: its two backend factories register their objects in a package-private registry (and carry a compile-time brand), `ModelBenchmarkStoreClient` throws on any other backend and cannot be subclassed, and `createModelBenchmarkRunner()` throws on any client that is not a genuine instance (a structurally similar object, a forged prototype, and a `Proxy` are all refused). The memory backend cannot mutate after an abort (its write is synchronous after the abort checks); the IndexedDB backend honors the signal from `open()` through the upgrade and the transaction. This removes accidental and structural ways to present an unsafe store as a safe one; it does not claim to stop in-process code that deliberately monkey-patches an instance.
- **Runtime ownership and isolation (shared with chat).** A runtime lease may only be released when all previous work is proven quiescent or physically isolated; there is exactly one logical owner, and recovery by the owner runs inside its own ownership scope instead of acquiring a second lease. When isolation cannot be proven the lease is quarantined: the coordinator refuses every ordinary operation and the quarantined lease's own `release()` is a no-op. `apps/web` enforces this for chat too: the watchdog recovers a hung generation UNDER the active generation lease (including a non-cooperative `sendMessage()`/Continue stream), a runtime is replaced only after the old worker is confirmed terminated (the new worker is never created first, so old and new workers do not overlap on a replacement path), and a failed isolation quarantines instead of releasing. "Confirmed terminated" means `Worker.terminate()` returned or resolved. A quarantine is lifted only by an explicit retry that re-confirms isolation. Recovery is two-phase: isolating the old worker is what releases a lease, while the replacement model load is separately bounded (`RECOVERY_REPLACEMENT_LOAD_TIMEOUT_MS`) -- on expiry the replacement worker is isolated too and recovery returns `{isolated: true, ready: false}` rather than holding ownership for an uncooperative `loadModel()` (both `sendMessage()` and Continue). A stall's reroute replacement uses the same bound and its result is folded into recovery's explicitly (final ready requires the replacement to initialize and the live runtime to report "ready"), so a failed replacement can never hide behind an earlier ready=true. Benchmark persistence is storage-only: the runtime lease is released before it starts, and a persistence failure never quarantines the runtime or blocks chat.
- **Subscribers cannot control the runner.** A throwing or rejecting `subscribe()` listener is contained per listener, so it cannot make a run fail, leak the active run, block consent, or prevent the next run.
- **An empty completion is never positive evidence.** Exact zero generated tokens, a token count contradicting a stream with no output, or unavailable usage with nothing observed all map to neutral `terminal_unknown`, never `completed`; stored zero-token `completed` records are classified neutral and excluded from throughput medians. A negative classification is reserved for positive failure evidence. Evidence STRENGTH counts informative samples only (positive plus genuinely negative): neutral and empty runs stay in the raw `compatibleSampleCount` history but never raise `evidenceLevel`.
