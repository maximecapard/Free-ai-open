# Architecture

## High-level design

```txt
Browser
├─ Next.js client UI
├─ WebLLM/WebGPU runtime in Web Worker
├─ IndexedDB local conversations
├─ Local JSON conversation export/import helpers
├─ Cache Storage / model cache
├─ Local logs
└─ Redacted telemetry client
       ↓
Netlify /api/telemetry
       ↓
Validation + redaction
       ↓
Technical telemetry persistence (planned)
```

## Data boundary

Private data stays in the browser:

- conversations;
- prompts;
- responses;
- uploaded documents;
- local preferences;
- local debug logs.

Server data is technical only:

- telemetry events;
- compatibility reports;
- model registry metadata;
- security events;
- public feedback.

## Packages

- `ai-runtime`: browser inference types/wrapper, runtime-only language instruction injection, stop/reload/recovery states, and alpha generation safety limits.
- `device-profiler`: capability estimation.
- `model-router`: task/mode/device based model selection.
- `model-registry`: model metadata and validation.
- `local-storage`: IndexedDB and local persistence.
- `conversation-store`: local-only browser conversation persistence, including an optional per-conversation `task` (usage/purpose) field.
- `conversation-export`: versioned local JSON conversation export/import helpers, preserving the optional `task` field under the same `freeai-open-conversations` version `1` format.
- `model-benchmark`: versioned local persistence and compatibility/invalidation helpers for `ModelBenchmarkResult` (v0.8.0-alpha "Local Benchmarks & Performance Intelligence" — contracts and architecture only in this phase; see below).
- `logger`: structured local logs.
- `privacy-redactor`: removes sensitive data.
- `telemetry`: event schemas and client/server helpers.
- `server-data`: placeholder for future server-side technical data persistence.

## Client/server rule

Browser-only code must never run in Server Components.

Browser-only APIs include:

- WebGPU;
- WebLLM;
- IndexedDB;
- Cache Storage;
- Web Workers;
- navigator APIs.

## UI language and theme

Translation and theme are app-level (`apps/web`) concerns, not packages, since they are tightly coupled to this app's specific UI strings and design tokens.

- Language: plain per-locale dictionaries (`apps/web/app/_i18n/locales/en.ts`, `fr.ts`) looked up through a small `useTranslations()` React context (`apps/web/app/_i18n`). No translation service or API call is involved; dictionaries ship as static data in the client bundle. The active locale defaults to the browser's language on first visit and is persisted in `localStorage`.
- Model response language: before local inference, `apps/web` passes the selected locale to `ai-runtime`, which adds a hidden system message to the WebLLM message list. This message is runtime-only: it is not conversation-store data, not displayed, not exported, not included in diagnostics, and not written to local logs. Language adherence is best effort and depends on model capability.
- Brand/design tokens: `apps/web/app/globals.css` defines the `--fo-*` token foundation from the FreeAI Open brand guide: source palette, semantic surfaces, text, borders, accent/focus, radii, spacing, typography, and motion durations. Existing `--color-*` variables remain as compatibility aliases; every current app surface (home, onboarding, chat, history, debug, settings) has been migrated onto the `--fo-*`/`.fo-*` foundation. Light-mode semantic text tokens deliberately separate visual brand teal from small text: `--fo-accent` can stay on the brighter brand teal for accents, while `--fo-accent-text` uses a darker accessible teal for normal-size labels, helper text, and badges.
- Application shell: `apps/web/app/_components/Header.tsx` renders a compact, always-Ink navigation rail on desktop and a compact fixed, safe-area-aware top bar with a small dropdown menu on mobile, both from the same markup — CSS alone (the same 720px breakpoint used by the chat drawer) decides which is visible. `apps/web/app/layout.tsx` wraps it and `{children}` in `.app-shell`/`.app-shell__content`. The rail/top bar are deliberately dark (`--fo-ink-950`) regardless of the selected theme, so the navigation chrome reads as stable structure while the main content area follows the theme normally. `/debug` uses the same technique for its whole page (see `.fo-ink-surface` in `globals.css`): rather than a separate "ink" variant of every class, `.fo-ink-surface` overrides the semantic `--fo-*` custom properties themselves within that subtree, so any existing token-based class or component resolves to the correct ink-forced colors automatically.
- Theme: CSS custom-property color tokens defined in `globals.css` for dark (default) and light, toggled via a `data-theme` attribute on `<html>` set by a `useTheme()` React context (`apps/web/app/_theme`) and persisted in `localStorage`. "System" leaves the attribute unset and relies on a `prefers-color-scheme` media query. A blocking inline script in the root layout applies a stored light/dark choice before hydration to avoid a flash of the wrong theme.
- Brand assets: production web PNGs live under `apps/web/public/brand/` and are referenced by the app metadata and compact navigation. Source brand files stay local-only under `.local/brand-source/` and are not part of the public repository. A true vector logo source is still future brand work.
- Neither system sends data to a server or stores anything beyond a small preference value (locale or theme name) in `localStorage`.

## First-run setup and per-conversation task

`apps/web/app/_lib/gettingStartedPreference.ts` is a single, schema-versioned `localStorage` record (`free-ai-open:getting-started`) holding whether the first-run "Getting Started" flow has been completed, the confirmed `PerformanceMode`, and an optional coarse device snapshot (`deviceTier`, `webgpuAvailable`, `formFactor`) kept only to explain the choice later — never raw sensor values. It follows the same window-guarded/try-catch convention as `themePreference.ts`/`localePreference.ts`, but bundles the whole flow's state in one record (rather than one key per field) since "has setup finished" and "what mode was chosen" are the same decision.

`/` and `/chat` both call `isGettingStartedCompleted()` on mount and redirect to `/onboarding` when it is false, so the first-run flow is shown automatically rather than offered as an optional shortcut. `/onboarding` has two steps: device detection plus an optional short benchmark (`/onboarding/device`, with cancel/skip) and performance-mode confirmation (`/onboarding/mode`). Before confirmation, the second step discloses the friendly compact compatibility model, its approximate first download size, local browser caching, and that every other uncached model requires separate consent. The previous third step, `/onboarding/task`, is removed — task selection moved to per-conversation (see below). Confirming a mode calls `completeGettingStarted(mode, deviceSnapshot)` and navigates straight to `/chat`; the mode can be changed later from `/settings`, which calls `setStoredPerformanceMode()` directly without touching the completion flag, and can reset the whole flow via `resetGettingStarted()`.

Each conversation now carries its own optional `task` (a `TaskCategory` value) in `ConversationMetadata`, set once when the conversation is created and never changed afterward. Selecting "New chat" opens `apps/web/app/_components/NewChatTaskDialog.tsx`, a small accessible modal (focus trap via a Tab/Shift+Tab keydown handler scoped to the dialog's own focusable elements, Escape and backdrop-click to close, background scroll lock while open, focus restored to whatever element was previously focused) that asks what the conversation is for using `apps/web/app/_lib/catalog.ts`'s existing `TaskCategory` catalog — never a separate list. `newChatTaskOptions` filters out `document_analysis`, since the product has no document upload/analysis entry point yet and offering it would promise a capability that doesn't exist. Selecting a task creates the conversation with that task already set, opens it, and closes the dialog; the performance mode is never re-asked here, since it is a global preference, not a per-conversation one.

`/chat` reads the performance mode from `gettingStartedPreference` and the active conversation's task from its own metadata (`resolveConversationTask()` in `catalog.ts` defaults a missing/invalid value to `"chat"`, covering conversations created before this field existed and conversations imported from an older export). Adaptive routing recomputes when task, locale, mode, capability/benchmark/cache evidence, or technical observations materially change. A model replacement is deferred while the runtime is busy and is a no-op when the selected model is already loaded, so a task/mode change never interrupts an in-progress generation.

## Desktop chat workspace layout

`/chat` has its own nested route layout, `apps/web/app/chat/layout.tsx`, which wraps the page in a `.chat-shell` div. This keeps the fixed-height, independently-scrolling treatment described below scoped to `/chat` alone — every other route continues to use the root layout's normal document-flow page scrolling untouched.

On desktop (`min-width: 721px`, the same breakpoint used everywhere else in the app), `globals.css` lets the root `.app-shell` own `height: 100dvh` for `/chat` while `.chat-shell` fills the remaining app-main height below any app-level runtime status strip. The conversation sidebar (`.chat-history-list`) and the message transcript (`.chat-main__scroll`) each get their own `overflow-y: auto` region, the composer (`.chat-main__composer`) stays `flex-shrink: 0` and anchored at the bottom, and every intermediate flex container along the chain is `min-height: 0` — the standard fix for a flex child otherwise refusing to shrink below its content's intrinsic height and defeating the inner `overflow-y: auto` regions. `ChatTranscript` measures the dedicated transcript scroll container on desktop and falls back to page scrolling on mobile. The page footer is hidden only on this route, and only inside the same desktop media query, via `.app-shell__main:has(> .chat-shell) + .app-footer { display: none; }` — a `:has()` selector rather than JS route-awareness, since the footer would otherwise either get clipped or force the shell taller than the viewport.

Mobile is untouched: none of the rules above apply below the 721px breakpoint, so the existing off-canvas history drawer, normal page scrolling, and footer all render exactly as before this change.

## Persistent runtime ownership

`apps/web/app/_runtime/AppRuntimeProvider.tsx` is a client component mounted from the root application layout, inside the locale/theme providers and above normal route boundaries. It owns the persistent runtime lifecycle, active generation identifiers, and current in-memory transcript view; focused `useAdaptiveRuntimeRouting.ts` owns adaptive decision/cache/consent/model-switch orchestration. `/chat` is a view over this provider rather than the owner of the worker.

The provider evaluates adaptive routing and loads the resulting safe candidate when the user first enters `/chat` with the saved Getting Started performance mode. A small legacy bridge still accepts valid `/chat?task=...&mode=...` links by recording the mode preference and, when no conversation is active yet, the task. New app flows no longer depend on query parameters. After the first load, normal internal navigation does not dispose the runtime:

- Chat -> Settings -> Chat keeps the loaded worker/model;
- Chat -> Debug -> Chat keeps the loaded worker/model;
- route component unmount is a no-op for runtime disposal;
- `document.visibilityState`/hidden-tab changes are not disposal triggers.

The public runtime status lifecycle remains `idle` (uninitialized/not started), `loading_model`, `ready`, `generating`, `cancelling`, `recovering`, and `error`. Explicit reload, performance replacement, and root disposal are internal lifecycle triggers rather than additional user-facing statuses.

Disposal is limited to explicit lifecycle events:

- the application root unmounts;
- the user explicitly reloads the model;
- recovery recycles a stuck or interrupted worker;
- a future performance/model transition actually requires replacing the worker/model.

The lifecycle controller (`persistentRuntimeLifecycle.ts`) wraps the existing bounded worker teardown helper, so replacement paths still call `runtime.dispose()` but always terminate the old worker within the configured grace period if unload hangs.

Active generation state is also provider-owned. Each generation carries a `generationId`, conversation ID, and assistant message ID; streamed chunks update the visible assistant message only while those identifiers still match. Returning to `/chat` therefore shows the current or completed response, while late chunks from stale generations are ignored. The final assistant response is persisted to `@free-ai-open/conversation-store` only after the existing completion rules allow it; stopped or unstable partial output is still discarded instead of saved as a completed answer. As of v0.7.1-alpha, a genuine watchdog-detected timeout/stall that already produced visible text is the one exception — see "Generation timeout and stall watchdog" below.

Changing global performance mode goes through `applyPerformanceMode()` on the provider. While the runtime is generating, cancelling, or recovering, Settings disables the save action and does not persist the new preference. When idle, a valid change persists the local preference, recomputes the adaptive decision, and replaces the worker/model only if the selected model actually changes; the same-model case remains a no-op.

Background browser execution is intentionally described as best effort. FreeAI Open does not unload the model merely because a tab becomes hidden, but browsers and mobile operating systems may still throttle or suspend background work.
## Runtime cancellation recovery

Stop/cancel is handled as a runtime lifecycle transition, not just a UI interruption:

1. `stopGeneration()` moves the runtime from `generating` to `cancelling` immediately and logs `inference.cancel.requested`.
2. A real abort confirmation logs `inference.cancelled`, but the interrupted runtime is not treated as safe/ready for a new generation.
3. The app enters `recovering`, records `runtime.recovery.started`, tears down the old worker with bounded termination, creates a new worker/runtime, and reloads the cached model.
4. The app returns to `ready` and logs `runtime.recovery.completed` only after the replacement runtime finishes loading the model.
5. If reload fails, the app records `runtime.recovery.failed` and exposes the existing Reload model action.

Late chunks or confirmations from an abandoned generation must not overwrite newer runtime state.

## Generation timeout and stall watchdog

A generation timeout means absence of runtime progress. It never means "the total generation duration exceeded a timer" while valid output was still arriving — that distinction is the entire reason `packages/ai-runtime/src/generationWatchdog.ts` exists (added in `v0.7.1-alpha`, fixing a release-blocking false timeout — see `docs/DEVLOG.md`'s Sprint 6.21 and `CHANGELOG.md`'s `[0.7.1-alpha]` entry).

`createGenerationWatchdog()` tracks one generation at a time (`packages/ai-runtime/src/runtime.ts` owns a single `currentWatchdog` per runtime instance, matching the existing rule that only one generation can be in flight). It models exactly two "no progress" phases, both measured from the latest real signal rather than from generation start:

- **First-token timeout** (`FIRST_TOKEN_TIMEOUT_MS`, 45s): active only from generation start until the first token/chunk arrives. It allows for model prefill/tokenization time and is permanently cleared — never re-armed — the moment the first chunk arrives.
- **Stall timeout** (`STALL_TIMEOUT_MS`, 45s): active only after the first token/chunk has arrived, and re-armed on every subsequent one. It detects a genuine gap with no new progress; a generation that keeps producing chunks, however slowly, never trips it. Whitespace/punctuation-only chunks still count as progress.

Both phases share one robustness rule: when a scheduled check fires, it recomputes real elapsed time against the latest recorded progress timestamp before doing anything. If the full inactivity window has not actually elapsed — for example because the callback itself fired late due to a busy main thread — it re-arms for the remaining time instead of declaring a false timeout. This makes the watchdog resilient to delayed event loops without relying solely on precise clear-and-recreate timer discipline.

Progress is recorded from the raw worker chunk the instant `generate()`'s `for await` loop receives it — before that chunk is even yielded to the caller, and therefore fully decoupled from `apps/web/app/_lib/streamingBuffer.ts`'s periodic UI flush (see "Streaming render responsiveness" below). A slow React render can never look like a stalled model, because the watchdog never waits on it.

**Total generation duration** remains available as a metric only; it is never itself a stall/timeout condition. A wholly separate, much larger, conservatively-sized `ABSOLUTE_GENERATION_SAFETY_LIMIT_MS` (10 minutes) exists purely as an emergency circuit breaker against a truly pathological runaway generation (e.g. one dodging the stall watchdog forever). It is a flat wall-clock timer, not reset by progress, and deliberately uses its own `generation_exceeded_safety_limit` error code — never `generation_stalled` — so it cannot be confused with a genuine inactivity stall. `apps/web/app/_lib/performanceObservationBuilder.ts` classifies this app-enforced cutoff as neutral `cancelled`, excluding it from router success, failure, and instability scoring.

**Generation-ID isolation.** Every `generate()` call creates its own `GenerationWatchdog` instance (closed over that call's own local progress timestamps) and captures the runtime's `generationEpoch` at start. A watchdog callback that does fire calls the shared `forceRecovery()`, which re-checks the epoch before touching any state. Forced errors are retained by epoch, and every raw stream chunk re-checks that epoch before processing content, so late chunks and terminal confirmations from an abandoned generation cannot affect a newer one. Completion, Stop, degenerate-output recovery, and full runtime disposal all dispose the current watchdog and clear the separate safety-limit timer, so no timer outlives the generation it was armed for.

**Background tabs.** `ai-runtime` stays platform-independent and never reads `document.visibilityState` itself; browser background-tab throttling can otherwise delay both timer firing and worker message delivery in ways indistinguishable from a genuine stall. `InferenceRuntime.setGenerationWatchdogSuspended()` lets the app layer pause inactivity detection entirely while hidden and grant a full fresh detection window on resume (rather than resuming a countdown that may already be most of the way expired), so a backlog of queued progress gets a chance to arrive before a stall could be declared. `AppRuntimeProvider.tsx` is the only caller, via a `visibilitychange` listener — matching the existing rule that FreeAI Open does not treat a hidden tab as a disposal trigger, but does not claim uninterrupted background execution is guaranteed by every browser.

**Outcome.** A genuine watchdog timeout stops/recycles the runtime the same way `cancel_timeout` already does, and records a technical-only failure observation (`generation_stalled`, never response content). If the interrupted generation had already produced visible assistant text, that partial reply is saved with durable `status: "incomplete"` metadata and rendered with an incomplete-response label. The provenance survives IndexedDB reload and local export/import; it is never copied to technical logs or diagnostics. An interruption with no output still discards the empty bubble.

## Reasoning output and finish reason

Added in `v0.7.1-alpha` alongside the reasoning-disclosure UI below (see `docs/DEVLOG.md`'s Sprint 6.21 "reasoning presentation and finish reason" subsections and `CHANGELOG.md`'s `[0.7.1-alpha]` entry), from a real, independently reported bug: a `qwen3-4b` generation persisted ending abruptly inside an unclosed `<think>` reasoning block with no final answer, yet was recorded as a normal `inference.completed` success.

**WebLLM's real finish reason, mapped exhaustively.** `@mlc-ai/web-llm`'s `ChatCompletionFinishReason` is `"stop" | "length" | "tool_calls" | "abort"`; its own documentation states `finish_reason: "length"` "indicates the generation exceeded `max_tokens`... or the conversation exceeded the max context length." Before this release, `packages/ai-runtime/src/runtime.ts` read `choice.finish_reason` only to detect `"abort"` — every other value, `"length"` included, fell through to the same `"completed"` outcome reported for a genuine natural stop. `runtime.ts`'s `mapFinishReason()` now handles every case explicitly through a switch with no catch-all branch, guarded by a compile-time `never` assertion in its `default` case: if `@mlc-ai/web-llm` ever adds a new finish reason, this function fails to compile until an explicit case is added, rather than silently mapping the new value to `"completed"`. `GenerationStopReason` (`packages/ai-runtime/src/types.ts`) has six values:
- `"completed"` — WebLLM's own `"stop"`, a genuine natural end of turn.
- `"length"` — the configured `max_tokens` budget was exhausted first.
- `"cancelled"` — a user Stop (WebLLM's `"abort"`) or a runtime-classified cancellation.
- `"degenerate_output"` — the app's own safety detector stopped generation; never a WebLLM finish reason.
- `"unsupported_tool_call"` — WebLLM's own `"tool_calls"`. FreeAI Open never passes a `tools` array to `engine.chat.completions.create()`, so this should not occur in normal operation, but if it ever does, it is surfaced as a response-shape limitation ("This response requires a feature FreeAI Open does not currently support yet.") — never scored as model instability, never silently accepted as a normal reply.
- `"unknown_terminal"` — the stream ended without ANY chunk ever carrying a `finish_reason` at all. Failing closed rather than assuming success: the runtime does not treat this as a crash (no `RuntimeError` is raised, since nothing about the worker/engine itself failed), but it is never folded into `"completed"` either.

The runtime still returns to `ready` for every one of these outcomes except `"cancelled"`/a real error — WebLLM itself did not error, so none of the ambiguous terminal reasons are ever scored as a stall or model-instability failure. `apps/web/app/_lib/performanceObservationBuilder.ts`'s `classifyGenerationOutcome()` maps `"length"`/`"unsupported_tool_call"`/`"unknown_terminal"` to their own distinct, neutral `ModelPerformanceObservation` outcomes (`"length_limited"`/`"unsupported_tool_call"`/`"terminal_unknown"` — see "Router observation semantics" below), and `apps/web/app/_lib/generationPersistence.ts` marks the message `status: "incomplete"` (with a matching `incompleteReason`, see "Reasoning disclosure and Continue" below) and preserves its partial output for all three.

**The real output-token limit.** Reproducing the reported case's binding limit required two separate mechanisms, neither of which alone explains it: (1) `@free-ai-open/model-router`'s `hasStrongPerformanceEvidence()` (existing, unchanged logic) falls back from the "performance" context/output preset to "balanced" (512 output tokens) whenever a model lacks enough completed observations yet — which an early-session generation, like the reported one, typically does, even with `performanceMode: "performance"` selected; and (2) a second, separate global ceiling, `GENERATION_SAFETY_LIMITS.maxTokens` in `packages/ai-runtime/src/generation-safety.ts`, was 768 — silently re-clipping even the full "performance" preset's 1024-token budget for 3 of the registry's 5 models via the existing `Math.min()` in `runtime.ts`'s `generate()`. Raised to 2048 so neither the router's existing presets nor the new reasoning allowance below are immediately re-clipped by this second, previously undocumented cap.

**Reasoning-aware output budget.** `packages/model-router/src/adaptiveOutputBudget.ts` adds a flat `REASONING_OUTPUT_ALLOWANCE_TOKENS` (512) on top of the selected preset's `maxOutputTokens`, but only for a candidate whose registry `family` reasons by default (`Qwen3` currently — the registry's existing `family` field already distinguishes this from `SmolLM2`/`Qwen2.5-Coder`). This is deliberately narrow, matching this hotfix's own scope: no model-registry schema change, and no change to `adaptiveRouter.ts`'s preset selection, model eligibility, or scoring — only the output-token budget number widens for models that actually need reasoning headroom, wired in via `recommendedMaxOutputTokens`.

**`enable_thinking` (not wired up).** WebLLM's chat-completion API accepts an `enable_thinking?: boolean | null` option; setting it to `false` prepends `<think>\n\n</think>\n\n` to suppress reasoning tokens entirely. This is a real, available lever for reducing reasoning-model output-budget pressure in a future release, but this hotfix deliberately does not wire it up — its scope is correctly presenting and budgeting for reasoning output that already happens, not deciding whether to request it. A future change enabling this must still respect the per-model/task/mode routing this document already describes rather than a single global toggle.

**Context-safe output budgeting.** Requesting the router's full recommended output budget regardless of input size can leave too little room in a small context window — a real case: Qwen3 in "fast" performance mode loads a 1024-token context but the preset alone can request up to 768 output tokens, leaving as little as 256 tokens for the system instruction, the user's prompt, and any conversation history. `packages/model-router/src/contextBudget.ts`'s `calculateGenerationBudget()` enforces `estimatedInputTokens + allowedOutputTokens + safetyMargin <= contextWindow`, tightening (never raising) the router's recommended budget.

Input-token counting was hardened in the second-round review after an initial character-based estimator (`characters / 3`) proved insufficiently conservative: a single accented letter, emoji, or CJK character can be 2-4 UTF-8 bytes while still counting as one JavaScript character, so dense Unicode, source code, and Markdown-heavy text could silently under-estimate the real token count. `estimateTokenCount()` now returns a string's UTF-8 byte length (`new TextEncoder().encode(text).length`) with no division at all. This is a genuine upper bound, not a rough guess, for every tokenizer family in real use by current open-weight chat models: byte-level BPE (the scheme behind GPT-2/3/4, and the LLaMA/Mistral/Qwen-family tokenizers) builds its vocabulary by merging adjacent bytes into single tokens, so merging can only ever reduce the token count relative to the raw byte count, never increase it, and no token can ever represent less than one byte — the same bound holds for SentencePiece-with-byte-fallback and character-level schemes. `estimateChatInputTokens(segments)` sums each non-empty segment's byte length plus a `CHAT_MESSAGE_OVERHEAD_TOKENS` (16) allowance per segment, covering the special tokens/role markers a real chat template wraps around every message (e.g. ChatML's `<|im_start|>{role}\n ... <|im_end|>\n`) that the raw text itself never contains. No public tokenizer or token-count API is available to count exactly instead: `@mlc-ai/web-llm` 0.2.84's public `MLCEngine`/`WebWorkerMLCEngine` classes — the only ones `ai-runtime`'s public surface uses — expose no `tokenize`/`countTokens`/`encode` method; the `Tokenizer` type from `@mlc-ai/web-tokenizers` exists only as a private field several layers inside `LLMChatPipeline`. `GenerationBudgetResult.confidence` is `"conservative"` today (renamed from an unconditional `"low"`) and would report `"exact"` only if a real per-model tokenizer becomes reachable from the app layer in the future — there is no code path that produces it today.

Every generation path now goes through the same resolver, including the case where routing has not yet produced a decision at all (e.g. the very first message before the performance-mode preference finishes loading, or before capability detection resolves — see `useAdaptiveRuntimeRouting.ts`'s `evaluateRouting()`, which can return `null`). This path previously skipped context-checking entirely, returning `maxOutputTokens: undefined` and falling back to `ai-runtime`'s own global `GENERATION_SAFETY_LIMITS.maxTokens` (2048) with no context check at all — more than the entire 1024-token "compatibility" context window some devices actually load. `apps/web/app/_lib/generationBudget.ts`'s `computeBudgetedOutputTokens()` (extracted from `AppRuntimeProvider.tsx` so it has direct unit-test coverage independent of React) now resolves this case through `calculateGenerationBudget()` too, assuming `FALLBACK_CONTEXT_WINDOW_TOKENS` — the smallest context window any registry model's presets could ever specify, derived from the live registry rather than a hardcoded literal — as the context window, and the global safety cap as the desired output. `finalOutput = min(desiredOutput, contextSafeOutput, globalSafetyLimit)` now holds identically whether or not a router decision exists.

`AppRuntimeProvider.tsx`'s `sendMessage()` and `continueGeneration()` both compute this before calling `runtime.generate()`; `continueGeneration()` refuses to start at all (showing "This conversation has grown too long for the local model to continue it. Try starting a new conversation.", no continuation attempt consumed) when the remaining budget would fall below a minimum useful floor (`MINIMUM_USEFUL_OUTPUT_TOKENS`) — Continue is the sharper case, since it re-embeds the entire prior partial reply as input (see `buildContinuationPrompt()`), so a long reasoning block leaves much less room than a fresh short prompt would. The existing global `GENERATION_SAFETY_LIMITS.maxTokens` cap (2048) remains only a final ceiling applied inside `runtime.ts`'s `generate()` — it is not itself a context-safety mechanism, since it knows nothing about input size.

**Router observation semantics.** `ModelPerformanceObservation["outcome"]` (`@free-ai-open/types`) includes `"length_limited"`, `"unsupported_tool_call"`, and `"terminal_unknown"` alongside the existing outcomes. All three are excluded from both `"completed"` (success) and instability scoring in `model-router`'s `adaptiveObservations.ts` (`NEUTRAL_OUTCOMES`, the same treatment `"cancelled"` already had) — a model that repeatedly hits its output budget must never look either more successful or less stable than it actually is. This replaces an earlier version of this fix that bucketed a length-limited generation as a plain `"completed"` success, which would have inflated the router's confidence in a model based on nothing but it running out of room.

## Streaming render responsiveness

The WebLLM worker stream is not throttled or modified. Streaming responsiveness is handled at the UI boundary in `/chat`:

- `apps/web/app/_lib/streamingBuffer.ts` batches visible assistant-text updates with `STREAM_RENDER_INTERVAL_MS` so very small token chunks do not trigger a React render for every chunk.
- `apps/web/app/chat/page.tsx` still accumulates the full assistant text in memory for completion handling and local persistence decisions. The buffer controls only when the transcript receives visible text.
- Pending buffered text is flushed on normal completion, cancellation, runtime error, or disposal so no characters are lost and no timer updates a stale assistant bubble after the generation path finishes.
- `apps/web/app/_lib/chatAutoscroll.ts` keeps scroll-follow behavior based on "near bottom" metrics. The transcript schedules scroll work through `requestAnimationFrame` and stops forcing scroll when the user has moved away from the bottom.
- The history drawer/sidebar/export controls and individual message bubbles are memoized so unchanged regions do not rerender for each buffered transcript update; language and theme still flow through React context.

The buffering layer is in-memory UI state only. It does not write generated text to local technical logs, diagnostic reports, telemetry, or any server path. Transcript virtualization remains future work for very long imported conversations.

## Message rendering

Added in `v0.7.1-alpha` alongside the watchdog fix above (see `docs/DEVLOG.md`'s Sprint 6.21 and `CHANGELOG.md`'s `[0.7.1-alpha]` entry): assistant Markdown renders as structured content instead of raw syntax. This is presentation-only — `@free-ai-open/conversation-store`/`@free-ai-open/conversation-export` and every generation code path in `AppRuntimeProvider.tsx` are unchanged, and the persisted/exported message content is always the original plain Markdown source string.

- **Renderer.** `apps/web/app/_components/MessageContent.tsx` wraps `react-markdown` with `remark-gfm` (tables) and `remark-breaks` (a single newline renders as a visible `<br>`, matching the previous `white-space: pre-wrap` line-break fidelity that a strict-CommonMark soft break would otherwise lose). `apps/web/app/_components/CodeBlock.tsx` renders fenced code in a dedicated Ink-surface component with a language label (parsed from the fence, a neutral "Code" label when absent) and a copy button (`apps/web/app/_lib/codeBlockCopy.ts`, a pure, unit-testable Clipboard API wrapper).
- **User vs. assistant.** Only assistant messages go through the Markdown renderer. User-entered messages remain plain text with preserved line breaks (`ChatTranscript.tsx`'s `ChatMessageBubble`) — an explicit decision: a pasted code snippet or a line a user typed starting with `*`/`#`/`` ` `` should never silently reformat. This is the same "least surprising" default most chat products with local Markdown rendering use.
- **Security model.** No `rehype-raw`/`rehype-sanitize` plugin is used, so raw HTML in the Markdown source (a `<script>`, an `onerror=` attribute, a `<style>` block) is dropped during the markdown-to-hast conversion rather than rendered; `dangerouslySetInnerHTML` is never used for model output anywhere in the app. Every link and image URL passes through `apps/web/app/_lib/markdownLinkSafety.ts`, a strict `http:`/`https:`/`mailto:` allowlist (`sanitizeMarkdownUrl`); anything else — `javascript:`, `data:`, `vbscript:`, `file:`, a bare relative or protocol-relative URL — resolves to an empty target, rendered as plain non-clickable text. External links always get `target="_blank" rel="noopener noreferrer nofollow"`. Markdown images are intentionally never rendered as `<img>` at all: displaying one is a real network request the browser makes on the model's say-so, which this local-first, privacy-first app never wants to trigger implicitly — the alt text/URL shows as safe text or a sanitized link instead. See `docs/security.md`'s "Markdown rendering" section for the full threat-model writeup.
- **Streaming tolerance.** `react-markdown` re-parses the full current message string on every buffered flush (not incrementally), so an unclosed ` ``` ` fence, an incomplete `**bold**` marker, or an in-progress list item never crashes, never blanks the message, and never loses streamed text — CommonMark parsers already treat an unterminated fence as extending to end-of-input. Because the whole string is re-parsed fresh each time rather than appending pre-rendered fragments, a later-arriving closing fence can never produce duplicated content. Markdown parsing happens only in this rendering layer; it never touches `packages/ai-runtime/src/generationWatchdog.ts`'s raw-chunk progress heartbeat (see "Generation timeout and stall watchdog" above), and reparse frequency is already bounded by the existing buffered-flush cadence (`streamingBuffer.ts`), not by every individual token.
- **Message isolation.** Each `ChatMessageBubble` renders its own message's content independently (memoized on that message's own object reference, matching the existing per-message memoization `persistentGenerationState.ts` already relies on); a malformed or unclosed fence in one message can never consume or alter another message, since messages are never concatenated before parsing.
- **No syntax highlighting.** Fenced code blocks render as clean, unhighlighted monospace text — deliberately, to avoid a large client-side highlighter dependency in this release. Layout and copy correctness take priority over colored tokens; richer highlighting remains future work.

## Reasoning disclosure and Continue

Added in `v0.7.1-alpha` alongside "Reasoning output and finish reason" above. A Qwen3 chat-template response can open with a `<think>...</think>` reasoning block before its final answer; this UI never shows that raw markup, and gives an interrupted reasoning block (see previous section) an explicit notice and a way to continue it.

- **Segmentation.** `apps/web/app/_lib/reasoningSegmentation.ts`'s `segmentReasoning()` is a plain string scan, not a general HTML/XML parser — `<think>` is a single well-known marker Qwen3 emits at the very start of its turn when thinking is enabled, never nested, never carrying attributes, so a full parser would be solving a problem that doesn't exist here. It returns `{beforeReasoning, reasoning, reasoningOpen, afterReasoning}`; a message with no `<think>` tag at all (most models, or a thinking-disabled request) is just `{beforeReasoning: content, reasoning: null, ...}` with no special handling. Presentation-layer only — it never mutates or re-saves persisted content, and every message is segmented independently, so a malformed tag in one message can never affect another (matching the existing per-message isolation guarantee in "Message rendering" above). `<think>` is recognized as a reasoning-opening marker only when it is the FIRST meaningful content of the assistant's output (ignoring only leading whitespace/newlines — `content.startsWith(THINK_OPEN, leadingWhitespaceLength)`), matching how Qwen3's chat template actually emits it; this was tightened in the second-round review from an earlier "first `<think>` anywhere outside of code" rule, since a response explaining raw HTML that happens to contain the literal text `<think>` later in ordinary prose (not necessarily inside a code span) could otherwise be mistaken for hidden reasoning. Requiring the leading position also structurally subsumes the old outside-of-code check for the OPEN tag, since a fence or a backtick span occurring first would itself already disqualify the leading position. A `<think>` occurring later — in prose, nested inside real reasoning, or anywhere else — is always literal text, and is never re-interpreted as opening additional hidden reasoning: only the first, leading `<think>`/`</think>` pair is ever treated as reasoning. The CLOSING `</think>` search remains Markdown-aware exactly as before: `findCodeRanges()` computes fenced-code (` ``` `/`~~~`, including an unclosed fence extending to end-of-input, matching CommonMark and this app's own streaming semantics) and inline-code-span ranges, and `indexOfOutsideCode()` only treats a `</think>` occurrence outside of those ranges — within a real leading reasoning block — as the real close, so a model showing example HTML/XML containing that literal text inside a code block while still reasoning does not prematurely end the reasoning segment. A real `<think>`/`</think>` pair the model itself emits is never inside code, so every historical/backward-compatible case is completely unaffected by this.
- **Rendering.** `ChatTranscript.tsx`'s `ChatMessageBubble` segments assistant content and renders `beforeReasoning`/`ReasoningDisclosure`/`afterReasoning` as three independent pieces, each still going through `MessageContent`'s existing safe Markdown renderer — reasoning can itself contain Markdown or code, and gets the exact same security guarantees described above. `apps/web/app/_components/ReasoningDisclosure.tsx` is a native `<details>`/`<summary>` panel (keyboard-accessible and touch-friendly with no extra JavaScript, unlike a custom accordion), expanded by default whenever `reasoningOpen` is true — covering both "still streaming" and "interrupted but open," so partial reasoning is never hidden by default — showing "Thinking…"/"Réflexion en cours…" while the message is the actively streaming generation (`isActiveGeneration`, passed down from `AppRuntimeProvider.tsx`'s `generation.assistantMessageId`) and the static "Thinking"/"Réflexion" label otherwise. It collapses itself exactly once, automatically, on the `reasoningOpen` true-to-false transition — extracted as a pure `didReasoningJustClose(previous, current)` function so the decision has direct unit-test coverage independent of React's render/effect lifecycle, called from a `useRef`-tracked-previous-value effect whose dependency array is exactly `[reasoningOpen]` (never `isOpen` itself), so a later manual reopen can never be forced shut again. The streaming label is wrapped in `aria-live="polite" aria-atomic="true"` so a screen reader hears "Thinking…" become "Thinking" without needing to refocus the disclosure; `.chat-reasoning__summary` gets a 44px minimum touch target on coarse-pointer/mobile viewports (`globals.css`, matching the code-block copy button's own target); the existing global `:focus-visible` rule already gives the summary a visible focus ring, and no open/close animation exists to need gating behind `prefers-reduced-motion`.
- **Interrupted vs. in-progress.** `isReasoningInterrupted(segments, isActiveGeneration)` is `segments.reasoningOpen && !isActiveGeneration`: a `<think>` block left open by a message that is no longer the active generation. When true, an explicit notice replaces the silence a reader would otherwise have to interpret themselves: a generic "The generation stopped before the final answer."/"La génération s'est arrêtée avant la réponse finale." for every case, and a length-specific "The generation limit was reached."/"La limite de génération a été atteinte." shown only when the reason is actually known to be `"length"`. This reason is durably persisted as `ConversationMessage.incompleteReason` (`@free-ai-open/conversation-store` — see "Durable incomplete-reason and continuation count" below), so the specific notice survives a reload, not only the generating session; a message from before this field existed (`incompleteReason` absent) correctly falls back to the generic notice. `ChatTranscript.tsx` also suppresses its existing generic "Incomplete response" label whenever `reasoningInterrupted` is true, so the two notices never stack.
- **Backward compatibility.** No migration step exists or is needed: `apps/web/app/_lib/continuationEligibility.ts`'s `isMessageContinuable()` and the segmentation/interruption logic above both work directly against raw stored content, so a conversation persisted before this feature existed — including one whose `<think>` block was left open by the exact bug this release fixes — renders correctly and offers Continue with zero code path specific to "old" data.
- **Continue.** A manual "Continue"/"Continuer" action (`AppRuntimeProvider.tsx`'s `continueGeneration`) is offered whenever `isMessageContinuable()` is true for the most recent assistant message: either an explicit `status: "incomplete"` (a length/stall/safety-limit/tool-call/unknown-terminal interruption recorded at persistence time), or — for a message persisted before that status field existed — a `<think>` block still open with no generation currently active. `runtime.generate()` only ever receives one `prompt` string per call and does not read prior conversation turns (see "Runtime disposal and recovery" for what it does track); `apps/web/app/_lib/continuationPrompt.ts`'s `buildContinuationPrompt()` therefore restates the original user request and the partial reply already produced, with an explicit "continue from here, do not repeat/restart" instruction in the UI's current language. This composed string is sent to the model only, is checked against the context-safe output budget above before the generation is even started, and is never itself persisted as a message, exported, or logged; only the model's newly streamed output is saved. Continue reuses the same `assistantMessageId` with a new `generationId` and does not reset the message's content — see "Generation accumulator" below for how the extended bubble is built and persisted. Bounded to `MAX_CONTINUATIONS_PER_MESSAGE` (3), durably tracked as `ConversationMessage.continuationCount` (persisted the instant an attempt starts, before any token is requested, so the bound survives a page refresh and a crashed generation still counts as a used attempt) — per the explicit design choice that a manual click is preferable to an invisible automatic retry loop, while still bounding how many times one message can be clicked through. Cancelling mid-continuation reverts the message to its exact pre-continuation content/status/incompleteReason (never the message itself, unlike a fresh reply in `sendMessage()`, since it already held a legitimate prior answer before the continuation began) and shows the same "stopped, not saved" notice as a fresh cancellation; the already-persisted continuation-count bump is not reverted, since the attempt was used the moment it started.

**Generation accumulator (generation output independent of queued React state).** Re-reading `messages` React state after the fact to decide what to persist is fragile: a state update queued via `setMessages` is not guaranteed to have committed by the time the next line of code runs, especially across the many `await` points a streaming generation crosses. `AppRuntimeProvider.tsx` instead keeps a `GenerationAccumulator` ref per in-flight generation — `priorContent` (the message's content before this attempt: `""` for a fresh `sendMessage()`, the existing partial reply for a continuation), `generatedDelta` (this attempt's raw tokens, accumulated verbatim), and `mergedContent` (`priorContent` merged with `generatedDelta` via `mergeContinuationOverlap()`, see below) — updated synchronously the instant each raw chunk arrives, before any buffered UI render. Every persistence decision (a normal completion, a watchdog-forced interruption, or a transactional Continue rollback) reads this accumulator, never `messagesRef.current`. `persistentGenerationState.ts`'s `setAssistantContent()` (replacing the old, purely-additive `appendAssistantChunk()`) always sets a message's content to an already-computed value from the accumulator, rather than appending onto whatever the message's content happens to already be.

**Continuation overlap deduplication.** A model asked to "continue from here" commonly repeats the tail of what it already wrote before actually adding new content. `apps/web/app/_lib/continuationMerge.ts`'s `mergeContinuationOverlap(priorContent, generatedDelta)` finds the longest EXACT suffix-of-`priorContent`/prefix-of-`generatedDelta` match within a bounded search window (400 characters) and removes only that overlap — never a fuzzy or semantic match, and never touching text that happens to repeat somewhere else in the reply (only the exact join point counts). The minimum overlap length is 24 characters (raised in the second-round review from an initial 3, which was found to be far too short in practice: a short match like a shared word ("the") or a shared code token ("});") is not reliably a duplicated-continuation artifact, and deleting it would silently destroy real content — strictly worse than leaving a rare, harmless duplicate in place. Below 24 characters, an exact join-point match is always kept, never trimmed; when in doubt, this function keeps the repetition. For a fresh, non-continuation generation, `priorContent` is always `""`, so the function reduces to a plain append — the same merge function serves both cases uniformly.

**Durable incomplete-reason and continuation count.** `ConversationMessage` (`@free-ai-open/conversation-store`) gained two fields, both optional and additive so every message that predates them keeps working unchanged: `incompleteReason` (`"length" | "unsupported_tool_call" | "unknown_terminal" | "stalled" | "safety_limit" | "truncated"`, computed by `apps/web/app/_lib/generationPersistence.ts`'s `incompleteReasonFor()`) and `continuationCount` (a non-negative integer). Both round-trip through `@free-ai-open/conversation-export`'s validation/export/import unchanged. `chat/page.tsx`'s conversation-import handler passes both fields (and `status`) through when creating imported messages — a gap in an earlier version of this feature silently dropped all three.

**Transactional Continue rollback.** The out-of-band watchdog-error effect in `AppRuntimeProvider.tsx` (the fallback path used when a forced-recovery error's stream never delivers its own terminal error chunk — see "Runtime disposal and recovery") reads the same `GenerationAccumulator` described above. For `cancel_timeout` specifically during a continuation, it reverts the message to its exact pre-continuation `content`/`status`/`incompleteReason` (both in React state and in `conversation-store`) instead of running the ordinary discard-the-message cleanup path that a fresh send's `cancel_timeout` still uses — `cancel_timeout` means this attempt's runtime state is not trustworthy, so keeping possibly-corrupted new output, or deleting a message that already held a legitimate prior answer, are both wrong. `generation_stalled`/`generation_exceeded_safety_limit` during a continuation instead preserve the accumulator's merged content (matching the existing fresh-send behavior of keeping genuine partial progress), marked incomplete with the matching reason. Persistence for a fresh send vs. a continuation is chosen from `GenerationAccumulator.isContinuation` (`updateMessageContent()` for a continuation, `addMessage()` for a fresh send) rather than a separate boolean ref, since the accumulator already carries this fact alongside everything else needed to act on it correctly.

**Continue orchestration is a plain, directly-testable function (second-round review fix).** The streaming loop, overlap merge, and outcome persistence for one Continue attempt are extracted from `continueGeneration()` into `apps/web/app/_lib/continuationExecution.ts`'s `runContinuationAttempt()`, and the watchdog rollback/preserve decision above into `apps/web/app/_lib/watchdogRecovery.ts`'s `runWatchdogRecovery()` — both plain `async` functions independent of React, returning their outcome as a value rather than through a mutable ref. This closes a real release-blocking bug: an earlier version of `continueGeneration()` called `setActiveGeneration(null)` (which clears the generation accumulator as a side effect) BEFORE reading the accumulator's `mergedContent` for the final persisted value, so a successfully-streamed continuation silently fell back to the pre-continuation content in both UI and IndexedDB. Returning the final content as this function's own resolved value, rather than reading a ref that a caller could clear first, makes that ordering mistake structurally impossible rather than merely fixed. This also gave the exact bug class direct regression coverage (`continuationExecution.test.ts`, `watchdogRecovery.test.ts`) without adding a DOM/React-testing-library dependency this repo does not otherwise have.

**Successful completion explicitly clears stale provenance.** `updateMessageContent()`'s `incompleteReason` parameter (`packages/conversation-store`) has three-way patch semantics: `undefined` leaves the field unchanged, a valid reason sets it, and `null` explicitly clears it — the field becomes genuinely absent from the stored/exported message, not merely `undefined`-valued in memory. Every call site that finalizes a continuation now passes `null` explicitly when the new state has no reason, so a continuation that completes successfully after being `"length"`-limited ends up with `status: "complete"` and no `incompleteReason` at all, never the invalid combination of a complete status with a stale reason held over from before the continuation ran.

**Local-storage truncation is surfaced everywhere it can happen.** `updateMessageContent()`/`addMessage()` (`packages/conversation-store`) both return `{ conversation, truncated }`; every caller reacts to `truncated: true` instead of some silently ignoring it — a user's own pasted message, a fresh assistant reply, a Continue result, the watchdog's preserved-partial-output path, and conversation import (`chat/page.tsx`) each show a notice distinct from the ordinary "output length limit reached" one: "This response exceeded the maximum size kept locally and was truncated." / "Cette réponse a dépassé la taille maximale conservée localement et a été tronquée." (`storageNotice.generationTruncatedForStorage`), plus a message-specific equivalent (`storageNotice.messageTruncatedForStorage`) and an import-summary equivalent (`backup.messageTruncated`). Conflating this with the existing `generationLengthLimited` notice (a model reaching its own output-token budget, where Continue is exactly the right next action) would have been misleading, since a message already truncated to the storage ceiling gains nothing from continuing — any new content would just be re-truncated back to the same ceiling — so `apps/web/app/_lib/continuationEligibility.ts`'s `isMessageContinuable()` now excludes `incompleteReason === "truncated"` explicitly, ahead of the general "any incomplete status is continuable" rule.

## Mobile navigation

Below a 720px viewport width, the `/chat` history panel (new chat, conversation list, rename/delete, export/import) is presented as an off-canvas drawer instead of a permanent block in the document flow:

- `apps/web/app/_lib/mobileHistoryDrawer.ts`: a pure reducer for the drawer's open/closed state, with distinct action types for each required closing trigger (open, close, toggle, selection, new chat, Escape, backdrop click, desktop viewport resize).
- `apps/web/app/_components/useMobileHistoryDrawer.ts`: a hook that wires the reducer to DOM behavior — Escape key handling, backdrop clicks, background scroll lock while open, focus transfer to the close button on open, background isolation with `inert` where supported, focus redirection back into the drawer if needed, focus restoration to the trigger button on close, and closing automatically if the viewport becomes desktop-sized.
- `apps/web/app/_components/ChatHistoryDrawerPanel.tsx`: wraps the existing `ChatHistorySidebar` (unchanged) with a backdrop, a mobile-only close button, and dialog semantics (`role="dialog"`, `aria-modal`, `aria-label`) that only apply at mobile viewport widths; the closed panel is marked `inert` on mobile so it isn't keyboard-reachable while off-screen.
- CSS in `globals.css` hides the trigger button, backdrop, and panel header by default and only shows them inside the existing `max-width: 720px` media query; the panel itself is a plain pass-through wrapper on desktop, so the fixed-width sidebar layout above that breakpoint is unchanged.

No JavaScript drives the desktop/mobile visual switch; a small `matchMedia` listener is used only to correct ARIA semantics and force-close the drawer if the viewport crosses the breakpoint while it's open.

The trigger button itself is `position: fixed` on mobile (top-right corner, offset by `env(safe-area-inset-top/right, 0px)`, above the drawer's own `z-index`), not just visually positioned in the heading row, so it stays reachable while scrolling through a long conversation instead of scrolling away with the page. `apps/web/app/layout.tsx` sets `viewport: { viewportFit: "cover" }` so those `env()` safe-area values actually resolve on notched/rounded-corner devices instead of silently evaluating to zero. `.chat-layout` gets matching top padding on mobile so the fixed button never overlaps the content underneath it, and the button toggles/hides itself while the drawer is open rather than staying visible above the open panel. Because the trigger is hidden while open, focus is moved into the drawer before the background is keyboard-reachable; closing through any existing close path restores focus to the trigger when it still exists.

## Device capability profiling

`@free-ai-open/device-profiler` builds a local, coarse capability profile used to pick a device tier (`0`–`4`, a plain `DeviceTier`) for `model-router`. As of v0.7.0-alpha Phase 1A, it also produces a `StaticCapabilityProfile` for the adaptive-router pipeline. This profile is still a static estimate: it uses browser-visible signals, never exact hardware specifications that the Web platform does not reliably expose.

The tier used to be derived almost entirely from `navigator.deviceMemory`, which classified any device with ≥8 GB of RAM as `webgpu_high` (tier 3) regardless of form factor — putting a 12 GB Android phone in the same tier as a desktop PC. The tier calculation is now a small, documented scoring model instead:

- `packages/device-profiler/src/capabilities.ts`: coarse, non-identifying detectors — `detectFormFactor` (`mobile`/`tablet`/`desktop`/`unknown`, from the UA-CH `mobile` hint and user-agent heuristics; the iPadOS desktop-style rule checks `Macintosh`/`Mac OS` plus `maxTouchPoints > 1` before generic macOS desktop classification, and contradictory hints fall back to `"unknown"`), `detectArchitectureClass` (`arm`/`x86`/`unknown`, from the Client Hints `getHighEntropyValues(["architecture"])` API when available — never guessed from OS family, since e.g. Apple Silicon Macs are ARM despite reporting `macos`), `classifyMemory`/`classifyCpuConcurrency` (bucket raw GB/core counts into `low`/`medium`/`high`/`unknown`), and `detectCpuConcurrency` (`navigator.hardwareConcurrency`).
- `packages/device-profiler/src/scoring.ts`: `getDeviceTier` gates tier `0` on WebGPU availability alone (unchanged from before — WASM-only devices stay at the most conservative tier). For WebGPU-capable devices, it sums small bounded points for memory class, CPU-concurrency class, and a fixed WebGPU baseline point (2 + 2 + 1 max — no single signal, least of all memory, can reach a high tier alone), then applies a **form-factor tier cap** (`mobile` capped at tier 2, `tablet` at 3, `unknown` at 3, `desktop` uncapped) so coarse signals alone can never place a phone alongside desktop-class hardware. An optional `measuredPerformance.tokensPerSecond` can promote a device above its cap (bounded by what the coarse signals already suggested), and a `measuredPerformance.recentFailureCount` of 2+ demotes the result by one tier, floored at tier 1.
- `DeviceProfile` now always includes `formFactor`, `architectureClass`, `memoryClass`, `cpuConcurrencyClass`, and an optional `measuredPerformance` echo. All of these are coarse, bounded categories or optional locally-supplied numbers — never a raw sensor value, a raw user-agent string, or anything that could act as a unique hardware fingerprint.
- `buildStaticCapabilityProfile()` produces the v0.7 `StaticCapabilityProfile` contract with schema version, detection/expiry timestamps, form factor, architecture class, browser/OS family, memory and logical-processor classes, WebGPU/WASM availability, fallback-adapter status, device tier, product-facing capability class (`compatibility`, `light`, `balanced`, `performance`), confidence, and a normalized `gpu` object.
- The normalized GPU object persists only coarse classes and buckets: vendor class (`nvidia`, `amd`, `intel`, `apple`, `qualcomm`, `arm`, `unknown`), broad architecture/description class, allowlisted feature classes, selected WebGPU limit buckets, fallback-adapter boolean, and optional low-confidence experimental memory bucket. Raw adapter strings, device IDs, driver strings, exact high-entropy limits, exact VRAM, and fingerprint hashes are never stored.
- The app writes this static capability profile through `apps/web/app/_lib/capabilityProfileStore.ts` when device detection runs on Home, onboarding, Settings, Debug, or the runtime provider. The store is schema-versioned, expires old profiles, and treats browser/OS-family changes as a reason to re-detect. Settings' existing "Re-check this device" action performs a fresh local detection.

### Plain-language presentation

`apps/web/app/_lib/deviceRecommendation.ts` adds `describeDeviceCapability(webgpuAvailable, deviceTier)`, a pure function mapping the raw tier to one of four public-facing categories ("Limited compatibility", "Suitable for lightweight models", "Recommended experience", "High-performance device") with boundaries that intentionally mirror `recommendPerformanceMode()`, so the label a user sees always matches the mode the app actually recommends. `apps/web/app/_components/DeviceCapabilitySummary.tsx` is the single shared presentational component (used on the home page and `/onboarding/device`) that shows this plain-language summary by default and keeps the raw tier/backend/memory/storage fields behind an "Advanced technical details" disclosure, matching the "simple by default, technical on demand" rule for the normal (non-technical) interface. `/debug` remains the one surface that shows raw technical values by default.

The home page's "Use the recommended setup" CTA also uses `apps/web/app/_lib/deviceRecommendation.ts` as its source of truth. Once `detectDeviceProfile()` resolves locally in the browser, `getRecommendedChatPath()` maps the current `DeviceProfile.deviceTier` to `/chat?task=chat&mode=<recommended>`. While profiling is still pending, the home page shows a detection state instead of hardcoding `balanced`. The `/onboarding/mode` recommendation badge consumes the same profile-to-mode helper, so home and onboarding cannot diverge without a test failure.

### Measured-performance integration

The v0.7 adaptive router consumes `StaticCapabilityProfile`, `LocalBenchmarkResult`, and recent `ModelPerformanceObservation` records directly. This lets real local load failures, stalls, first-token timing, and generation timing adjust decisions without turning a coarse profiler tier into an exact hardware claim. The older optional `DeviceProfilerEnvironment.measuredPerformance` hook remains unwired; no caller invents token-rate data. As of v0.8.0-alpha Phase 1 (see below), `@free-ai-open/ai-runtime` itself can now capture real tokenizer-backed usage per generation — but nothing yet reads it into a `ModelPerformanceObservation`, so `promptTokensPerSecond`/`generationTokensPerSecond` on THAT contract still stay absent until a future phase wires the two together.

## v0.7.0-alpha — Adaptive Router v1 phases

**Status: Phases 0 through 6 are implemented.** `AppRuntimeProvider` computes a `RouterDecision` before the first model load and applies it — including safe model switching and real observation recording — and `/settings` exposes automatic/manual model selection with a plain-language chat explanation. `/debug` reads that same live decision and loaded model rather than constructing a second preview.

### Contract types and where they live

- `@free-ai-open/types` (`router-signals.ts`): `CapabilityConfidence` (`"low" | "medium" | "high"`, shared by every signal below), `StaticCapabilityProfile` (a device's static, non-benchmarked capability signals — form factor, architecture class, coarse memory/processor counts, WebGPU/WASM availability, and a `gpu` sub-object of coarse classes and bounded feature/limit maps, never a raw adapter string), `LocalBenchmarkResult` (a short local microbenchmark's outcome, with an `expiresAt` so a stale result can be treated as absent), and `ModelPerformanceObservation` (a single observed model load/generation outcome — technical timings and an outcome code, never prompt/response content).
- These four types live in `@free-ai-open/types` rather than in `device-profiler`/`ai-runtime`/a future `local-benchmark` package individually, specifically so every future producer (a capability detector, a benchmark runner, `ai-runtime`) and consumer (`model-router`) can share one contract without any of those packages depending on each other. In particular, `model-router` — meant to stay pure eligibility/scoring/fallback logic — never needs a dependency on the much heavier `ai-runtime` package (which pulls in `@mlc-ai/web-llm`) just to reference `ModelPerformanceObservation`.
- `FormFactor`/`ArchitectureClass` moved from `device-profiler` into `types` as part of this (device-profiler re-exports both, so every existing `import type { FormFactor } from "@free-ai-open/device-profiler"` call site is unaffected) — `StaticCapabilityProfile` reuses the exact same coarse categories as the existing `DeviceProfile` instead of a parallel duplicate definition.
- `@free-ai-open/model-router`: the adaptive implementation is split across normalization, observation aggregation, eligibility, scoring, fallback, and orchestration modules. `routeAdaptiveModel()` is pure and deterministic for a normalized input, registry version, and clock. Its stable reason/warning/rejection codes are translated by the app for normal and debug surfaces.
- `@free-ai-open/model-registry` (`schema-v2.ts`, `registry-v2.ts`, `registry-validation.ts`): `ModelRegistryRecord`, strict runtime validation, and five curated records verified with WebLLM `0.2.84`. Records carry sourced download/runtime estimates, ordered context presets, per-language/task/form-factor/performance-mode scores, capability gates, source/license metadata, known issues, and validated acyclic fallbacks. The package imports WebLLM only in tests to compare exact prebuilt IDs, URLs, libraries, features, and memory metadata; production registry code stays metadata-only. The active adaptive runtime uses `modelRegistryV2`; legacy records remain only for backwards-compatible package tests/helpers.

### Registry and runtime boundary

Model Registry v2 is metadata, not the selector itself. It validates records at module initialization and exposes only fully verified records to the adaptive router. It does not inspect the device, load a model, download an artifact, persist a preference, or call the network. WebLLM remains behind the client-only `ai-runtime`/worker boundary.

The fixed Phase 0 test default changed to the verified `SmolLM2-360M-Instruct-q4f32_1-MLC` compatibility record. As of Phase 4, this record serves as the pre-disclosed fallback: when the router's preferred uncached model needs consent, the runtime attempts the disclosed compact record first so chat can remain usable while the optional upgrade waits. Every subsequent switch resolves through `RouterDecision`; normal runtime errors still surface if even the compatibility model cannot load.

### Persistence boundaries

Three local, schema-versioned preference stores live in `apps/web/app/_lib/`: `capabilityProfileStore.ts`, `benchmarkResultStore.ts`, and `modelObservationStore.ts`. They rebuild exact allowlisted shapes and reject stale, version-mismatched, profile-mismatched, malformed, or unexpected data. Real load and generation observation writers are active, and the capped observation store never accepts arbitrary extra fields.

Matching the mission's recommended boundaries:

- **Session-only, never persisted:** raw GPU adapter strings, exact high-entropy limit maps, active benchmark buffers.
- **Persisted locally:** the coarse `StaticCapabilityProfile`/`LocalBenchmarkResult`/`ModelPerformanceObservation[]` shapes above, plus the existing `gettingStartedPreference` (performance mode) and per-conversation `task`.
- **In diagnostics:** coarse capability categories, benchmark version/status/score, current recommended/loaded model IDs, technical errors/logs/metrics. The `/debug` UI may additionally display the in-memory router reason codes and observation summary; the exported report still contains no conversation content.
- **Never:** prompt, response, conversation, document content, a unique device fingerprint, or the hidden runtime-only language instruction.

### Local benchmark package boundary

`@free-ai-open/local-benchmark` depends only on `@free-ai-open/types`. It owns workload selection, deterministic WebGPU execution, scoring, stability classification, timeout/cancellation handling, and resource cleanup. `apps/web` owns Worker creation, local persistence, lifecycle logs, and UI. The package does not depend on or share a device with `ai-runtime`.

### Dependency graph verified for this phase

No new inter-package dependency edge was introduced: `types` remains a zero-workspace-dependency leaf; `device-profiler`, `model-registry`, and `model-router` already depended on it. `apps/web/app/_lib/packageDependencyBoundaries.test.ts` reads each package's real `package.json` and asserts this holds — including that `model-router` does not depend on `ai-runtime` and vice versa — so a future phase that does add a real edge gets a test failure if it accidentally creates a cycle.

### Phase 4 — Runtime integration

`apps/web/app/_runtime/AppRuntimeProvider.tsx` now owns the full routing lifecycle instead of unconditionally loading the fixed default:

- **Deciding.** `useAdaptiveRuntimeRouting()` builds a `RouterInput` (via `routingOrchestration.ts`'s `buildRouterInputContext()`, which reads the stored capability profile — detecting fresh only if none is valid — the stored benchmark for that profile, stored observations, and real per-model cache status) and calls `routeAdaptiveModel()`. It only recomputes when `apps/web/app/_lib/routingDecisionCache.ts`'s cache key actually changes (task, locale, performance mode, capability/benchmark timestamps, cached-model set, registry version, or the revision of technical observations) — never before every message. Explicit benchmark/profile/history controls invalidate the key, and a completed generation re-evaluates it so repeated failures can affect the next safe model choice. The decision is kept in React state/refs only, never written to `localStorage`.
- **ID spaces.** A `RouterDecision`'s `selectedModelId`/`fallbackModelIds` and every stored `ModelPerformanceObservation.modelId` are registry IDs (matching how `adaptiveRouter.ts` itself matches observations, `item.modelId === model.id`), but `InferenceRuntime.loadModel()`/`RuntimeState.modelId` are WebLLM model IDs. `routingOrchestration.ts`'s `buildLoadCandidatesFromDecision()`/`registryIdForWebllmModelId()` bridge the two spaces at every call site so a load is always requested by WebLLM ID while every recorded observation stays keyed by registry ID.
- **Switching.** `apps/web/app/_lib/modelSwitchPolicy.ts`'s `resolveModelSwitch()` decides what happens when the decision's pick differs from what's loaded: the same model is a no-op; a busy runtime (loading, generating, cancelling, or recovering) defers until the next routing moment; a cached model or the pre-disclosed default (`SmolLM2-360M-Instruct-q4f32_1-MLC`) switches immediately via `performModelSwitch()` (a `model_replacement` runtime-disposal trigger, reusing the existing safe worker-teardown path); anything else shows a `ModelDownloadConsent` prompt before anything downloads. The default's friendly name, approximate size, and local-cache behavior are disclosed in first-run setup. Declined and failed upgrade IDs are retained for the current session so the same prompt/load cannot immediately loop.
- **Loading with fallback.** `attemptModelLoadWithFallback()` walks a bounded candidate list, stopping at the first successful load and recording one technical load observation per attempt. Before loading, `filterDisclosedLoadCandidates()` removes any candidate that is neither cached, explicitly approved, nor first-run pre-disclosed, so fallback cannot become a silent new download.
- **Observations.** Load observations come from `attemptModelLoadWithFallback()`; generation observations are built in `sendMessage()` from locally measured wall-clock timing (`firstTokenTimeMs`, `generationDurationMs`) plus the stream's `stopReason`/error code. Load attempts and generation outcomes are aggregated with separate denominators. User cancellation is excluded from instability rates; repeated stalls, OOM, or device-loss outcomes can reject a model. `promptTokensPerSecond`/`generationTokensPerSecond` are not populated because the runtime does not expose real token counts, and character counts are not substituted.
- **Generation limits.** `RouterDecision.recommendedMaxOutputTokens` threads through to `ai-runtime`'s `generate({ maxOutputTokens })` and can only tighten the existing `GENERATION_SAFETY_LIMITS.maxTokens` cap. `recommendedContextTokens` is passed to WebLLM engine creation as `context_window_size`, capped by the verified maximum context preset of every load candidate.
- **Cache detection.** `ai-runtime` gained `isModelCached()`, a thin wrapper over WebLLM's `hasModelInCache()`. It defaults to `false` (assume a download is needed) on any failure, since that direction only ever triggers an extra consent prompt rather than an undisclosed download.
- **Manual override.** `RouterInput.manualModelId` stays wired through every function used above; Phase 5 supplies it from the app layer — see "Phase 5 — Router UI" below.
- **Diagnostics.** `/debug` reads `AppRuntimeProvider`'s live adaptive decision, selected model, loaded model, runtime status, task, performance mode, and selection mode. Its adaptive panel shows confidence, translated reasons/warnings, fallback chain, rejections, and token budgets, plus a local observation summary. Exported diagnostics use the same live technical IDs/status and still pass through the strict privacy builder.

### Phase 5 — Router UI

The mission's principle: "simple by default, technical on demand." Every technical panel this phase adds is opt-in (`/settings`, `/debug`) or behind a `<details>` disclosure; the normal `/chat` surface gained only a one-line plain-language explanation and richer status wording.

- **Manual override.** A new local preference store, `apps/web/app/_lib/manualModelPreference.ts` (`{mode: "automatic" | "manual", manualModelId}`, schema-versioned, mirrors `gettingStartedPreference.ts`), is loaded into `AppRuntimeProvider` on mount and threaded into every `evaluateRouting()` call as `RouterInput.manualModelId`. `setManualModel()`/`setAutomaticModel()` persist the choice, update state, and immediately trigger a re-route + `applyModelSwitchIfNeeded()` — manual selection goes through the *same* consent flow as automatic routing (`resolveModelSwitch()`); picking a model by hand is not itself consent to download it, and the router still applies its own hard eligibility gates regardless of what was manually requested (warning rather than bypassing them if the pick turns out ineligible).
- **Manual model picker.** `apps/web/app/_components/ManualModelPicker.tsx` (used from `/settings`) lists an "Automatic — recommended" option plus one card per `modelRegistryV2` record: localized friendly name, approximate size, live cache status (`isModelCached()` per model), a technical-details disclosure (exact WebLLM ID, per-language suitability, recommended tasks, device suitability), and an experimental-status note. Cards fail closed while no capability-backed decision exists, then remain disabled — not hidden — for the router's rejected models with the router's own reasons. The selectable area and the details disclosure are siblings, and the disclosure summary has a 44px touch target.
- **Friendly recommendation line.** `apps/web/app/_lib/friendlyRouteExplanation.ts`'s `pickFriendlyRouteExplanation()` reduces a `RouterDecision.reasons[]` list to exactly one plain-language sentence via a fixed priority order. Chat shows it only when the recommended model is the model actually loaded; a pending recommendation is not described as active.
- **Model status labels.** `apps/web/app/_lib/modelStatusLabel.ts` resolves active loading/recovery/error states before pending routing or consent. This prevents a pending upgrade prompt from replacing real "Preparing" progress. `ModelStatusPill` separately names the loaded model and recommendation, so a compact fallback is never labelled as an unloaded recommendation.
- **Download consent refinements.** `PendingModelSwitch` includes mobile form factor for the ≥500MB mobile-data warning. `ModelDownloadConsent` uses localized friendly model names and truthful inline-region semantics rather than claiming modal focus behavior it does not implement.
- **Empty/error states.** `apps/web/app/_lib/chatEmptyState.ts`'s `resolveChatEmptyStateReason()` distinguishes three chat-relevant causes from a `RouterDecision`: every rejected model blocked specifically by `backend_unavailable` → a WebGPU-specific notice instead of the generic "no compatible model" one; a `manual_model_ineligible`/`manual_model_unknown` warning even though a fallback was still selected → a notice that the manual pick was overridden this time; otherwise the existing generic notice. A new `useOnlineStatus()` hook (`apps/web/app/_components/useOnlineStatus.ts`) adds an offline-specific line to the existing model-unavailable error banner when `navigator.onLine` is false.
- **Debug additions.** The Phase 4 adaptive-router panel includes per-model cache status and the provider's real automatic/manual mode. Recommended model, loaded model, runtime status, task, and diagnostic export values all come from the same persistent runtime context.

## v0.8.0-alpha — Local Benchmarks & Performance Intelligence (Phase 0: contracts and architecture; Phase 1: runtime-backed metrics)

**Status: Phase 0 and Phase 1 only.** Phase 0 defines the versioned data contract, metric semantics, persistence architecture, and (non-wired) router relationship for user-visible MODEL performance benchmarking. Phase 1 (see its own section below) extends `@free-ai-open/ai-runtime` so a real generation can produce the accurate measurements a future benchmark runner will consume. No benchmark runner exists yet, no `/benchmarks` page exists yet, and nothing in this section changes how the adaptive router actually scores a model today — see "Local Benchmarks & Performance Intelligence (v0.8.0-alpha phases)" in `docs/roadmap.md` for what remains.

This is deliberately NOT `@free-ai-open/local-benchmark`/`LocalBenchmarkResult` (see "Local benchmark package boundary" above): that is a generic WebGPU compute microbenchmark, measuring raw device throughput independent of any model, and is unchanged by this work. A `ModelBenchmarkResult` instead measures one ACTUAL local model's real behavior on this device/browser: how long it took to load, how long until the first token, what generation speed was achieved, and whether the run was stable — the same category of question `ModelPerformanceObservation` already answers from incidental real chat usage, but from a deliberate, bounded, user-initiated run instead.

### Contract types and where they live

- `@free-ai-open/types` (`benchmark-signals.ts`, a file separate from `router-signals.ts` — see its own top comment): `ModelBenchmarkPreset` (`"quick" | "standard" | "extended"` — the run's own scope/thoroughness, not to be confused with `PerformanceMode`, which describes how a user wants REAL chat generations to trade off speed vs. quality), `ModelBenchmarkContextPreset` (mirrors `@free-ai-open/model-registry`'s `contextPresetIds` by value, duplicated rather than imported so this leaf package stays dependency-free), `ModelBenchmarkOutcome` (the exact same type as `ModelPerformanceObservation["outcome"]`, not a parallel union — a benchmark run and a real generation can end in exactly the same set of ways, and reusing the identical type means a future addition to that vocabulary keeps both in sync by construction), and `ModelBenchmarkResult` itself with its sub-shapes (`ModelBenchmarkModelReference`, `ModelBenchmarkRunConfig`, `ModelBenchmarkLoadMeasurement`, `ModelBenchmarkFirstTokenMeasurement`, `ModelBenchmarkGenerationMeasurement`, `ModelBenchmarkEnvironment`).
- Lives in `@free-ai-open/types` for the same reason `router-signals.ts`'s contracts do: a future benchmark runner (likely inside or alongside `ai-runtime`), the new `@free-ai-open/model-benchmark` persistence package, `model-router` (for later interpretation), and the UI can all share this one contract without any of them depending on each other.
- `modelId` is duplicated at the top level of `ModelBenchmarkResult` (alongside the fuller `model: ModelBenchmarkModelReference` reference) purely for indexing convenience, matching how `ModelPerformanceObservation.modelId` and `RouterDecision.selectedModelId` already work — every consumer can filter/join by model without reaching into a nested object first.

### Metric semantics

- **Load time.** `ModelBenchmarkLoadMeasurement.loadTimeMs` is measured from the model-load request to the runtime reporting ready — a single "everything the load step took" number, deliberately not split into a separately-measured download phase: download time cannot be measured consistently across browsers/CDN/cache conditions, so this contract does not claim a precision it cannot deliver. `wasModelCachedBeforeRun` and `modelLoadedDuringRun` together distinguish three real cases: a fresh, uncached download+load; a cached-but-cold load (already downloaded, still had to initialize); and a model that was already loaded and ready before the benchmark started, in which case `loadTimeMs` is absent entirely — there was nothing to time.
- **Time to first token.** `ModelBenchmarkFirstTokenMeasurement.firstTokenTimeMs` is measured from inference start (the moment generation is requested, not the moment the model finished loading) to the earliest raw token/chunk the runtime itself reports. It must never depend on React rendering or any buffered transcript update — see "Streaming render responsiveness" above for the existing buffering layer this measurement is independent of, exactly like `ModelPerformanceObservation.firstTokenTimeMs` already is.
- **Generation throughput.** `ModelBenchmarkGenerationMeasurement.tokenCountConfidence` is `"exact"` only when a real runtime/tokenizer-backed generated-token count is available, `"unavailable"` otherwise — there is no third, approximate tier. `generatedTokenCount`/`generationTokensPerSecond` are only ever populated (and only ever trusted, see `@free-ai-open/model-benchmark`'s `validation.ts` below) when confidence is `"exact"`. A character-length-derived tok/s is explicitly disallowed as authoritative, matching this codebase's existing rule (see "Measured-performance integration" above: `promptTokensPerSecond`/`generationTokensPerSecond` stay absent until the runtime exposes real counts, and character counts are never substituted).
- **Completion duration.** `generationDurationMs` is a separate field from both TTFT and throughput — total wall-clock time for the generation step, independent of whether a token count was ever available.
- **Stability.** `@free-ai-open/model-benchmark`'s `classifyModelBenchmarkStability(outcome)` groups `ModelBenchmarkOutcome` into `"positive"` (`completed`), `"neutral"` (`cancelled`, `length_limited`, `unsupported_tool_call`, `terminal_unknown` — a user-cancelled benchmark run must never penalize the model, and neither must one that merely exhausted its own output budget or hit an unsupported response shape), and `"negative"` (`stalled`, `degenerate`, `out_of_memory`, `device_lost`, `load_failed`) — deliberately mirroring `model-router`'s own `adaptiveObservations.ts`'s `NEUTRAL_OUTCOMES` set exactly, in both membership and philosophy. This classification is a pure function computed fresh from `outcome`, never persisted on `ModelBenchmarkResult` itself, so a future refinement of the rules applies retroactively to every already-stored result rather than requiring a migration.

### Benchmark presets

Only `"quick"` is expected to ship a real runner first (Phase 1, not yet started): a single bounded sample — load (if needed), first token, and a short generation — with a strict maximum duration and output/context limits, cancellable, and never silently downloading an uncached model without the same disclosure/consent flow "Switching"/"Loading with fallback" above already require. `"standard"`/`"extended"` are reserved in the type now (multiple samples/a longer generation for a steadier average, not a fundamentally different measurement) specifically so the contract does not need to change again once they are built. This release does not benchmark answer "quality" with subjective prompts — this is a performance/stability measurement, not a model-answer evaluation.

### Persistence and package boundary

`@free-ai-open/model-benchmark` (new package, depends only on `@free-ai-open/types`) owns everything about storing and validating `ModelBenchmarkResult` history — mirroring `@free-ai-open/conversation-store`'s own architecture closely enough to be immediately familiar. `apps/web/app/_lib/packageDependencyBoundaries.test.ts` (previously v0.7.0-alpha router/runtime/registry only) now also asserts this package's boundary directly: it depends on nothing but `@free-ai-open/types`, has no dependency edge to `model-router`/`ai-runtime`/`model-registry`, and introduces no cycle.

- `indexed-db-store.ts`/`memory-store.ts` implement one shared `ModelBenchmarkStore` interface (an IndexedDB-backed object store with a `modelId` index for efficient per-model queries/clearing, and an in-memory fallback for SSR/tests) — exactly `conversation-store`'s `ConversationStore` pattern. Neither backend is exported from the package's public `index.ts`: they are an internal implementation detail, reachable only via relative import within the package itself (its own tests, and `client.ts`'s composition). `ModelBenchmarkStoreClient` is the only way anything outside the package can persist or read a result — a caller cannot reach a raw, unsanitized write path.
- `validation.ts`'s `sanitizeModelBenchmarkResult()` rebuilds a brand-new object from allowlisted fields only — never the caller's own input reference — and re-validates every record on both write and read: a record from an unsupported (past or future) `schemaVersion` or `benchmarkVersion`, or with an impossible value anywhere (a negative or non-finite timing, an unknown outcome/stage/preset, a top-level/nested `modelId` mismatch), is dropped entirely rather than partially trusted or coerced — deliberately STRICTER than `apps/web/app/_lib/modelObservationStore.ts`'s own per-field-drop leniency for incidental usage observations, since a benchmark result is deliberate, infrequent, higher-stakes evidence: a record containing one impossible value calls the whole measurement pipeline into question, not just that one field. The one exception is `generatedTokenCount`/`generationTokensPerSecond` when `tokenCountConfidence` is `"unavailable"`: those two fields are not invalid in that case, they are simply out of scope (and are not even nameable properties on that branch of the type — see `ModelBenchmarkGenerationMeasurementUnavailable` above), and are dropped without rejecting the record. Beyond field-level validation, this function additionally enforces cross-field invariants a type alone cannot express:
  - **Exact-throughput consistency (item closing the "misleading tok/s" gap).** When `tokenCountConfidence` is `"exact"`, `generatedTokenCount` must be a finite, non-negative INTEGER, `generationDurationMs` must be finite and strictly positive, and `generationTokensPerSecond` must be finite, non-negative, and numerically consistent with `generatedTokenCount / (generationDurationMs / 1000)` within a small explicit tolerance (2% relative, 0.05 tok/s floor) — a plausible-looking but fabricated or character-length-derived rate is rejected exactly like any other impossible value, never merely asserted.
  - **Coarse, non-fingerprinting `capabilityProfileKey`.** Validated against the exact same low-entropy, four-segment grammar `buildCapabilityProfileKey()` produces (form factor / capability class / WebGPU availability / adapter kind, each drawn from its own small allowlist) — an arbitrary bounded-length string, a UUID, or an exact GPU adapter description can never pass, closing a fingerprinting-key gap a bare length check previously left open. `browserFamily` is intentionally not one of the key's segments, since it is already its own separate field.
  - **Exact, non-forgeable expiry.** `expiresAt` must equal `calculateModelBenchmarkExpiry(createdAt)` — `createdAt` plus `MODEL_BENCHMARK_DEFAULT_TTL_MS` — EXACTLY, computed by one canonical helper (`expiry.ts`). A stored or forged `expiresAt` that does not match this formula (including a far-future value) is rejected outright, and `createdAt` itself is rejected if it is in the future relative to the caller-supplied `now`.
  - **Legal stage/outcome/measurement combinations.** An explicit lookup table (`LEGAL_STAGE_OUTCOMES`) enumerates which `ModelBenchmarkOutcome`s are possible for each `ModelBenchmarkStage` (e.g. `not_started` only ever pairs with `cancelled`; a load failure can never coexist with generation metrics), and further cross-field checks enforce that `firstTokenTimeMs` is present exactly when the stage implies at least one token arrived, that a stage which never reached generation carries no generation duration or exact-count measurement, and that a run reaching `complete` always has a `generationDurationMs` (a wall-clock duration is always computable once the loop has ended, even without an exact token count). This is a deliberate, narrower alternative to a full discriminated-union rewrite of `ModelBenchmarkResult` itself — the mission explicitly permits "an equivalent exhaustive invariant layer," and this validation-layer table changes far fewer call sites for the same guarantee.
- `client.ts`'s `ModelBenchmarkStoreClient` owns migration-on-read (re-running `sanitizeModelBenchmarkResult()` over every stored record so a schema change never surfaces a partially-typed shape), `clearAll()`, and `clearForModel(modelId)`. History-cap enforcement (`MAX_STORED_BENCHMARK_RESULTS` = 100 total, `MAX_STORED_BENCHMARK_RESULTS_PER_MODEL` = 20 — oldest dropped first, per-model before global) lives in each storage backend's own `putAndPrune()`, not in the client: the insert and the prune happen as one atomic operation per backend (a single IndexedDB readwrite transaction that resolves only on `transaction.oncomplete`, never merely on the last request's `onsuccess`, and rejects on `onabort`/`onerror`; a synchronous, therefore trivially atomic, in-memory update), so there is never an externally observable state where a new record was written but the cap was not yet enforced, or vice versa. Both backends share one pure eviction-selection function (`pruning.ts`'s `computeModelBenchmarkIdsToPrune()`) so they can never drift into different eviction semantics.
- `compatibility.ts` defines the invalidation contract: `isModelBenchmarkResultExpired()` (past its `expiresAt`), `isModelBenchmarkResultCompatible()` (this package's own current `benchmarkVersion` constant, plus the CURRENT registry version, WebLLM version, capability-profile key, AND browser family, must all match the result's recorded ones exactly — any single mismatch invalidates it, never a partial/fuzzy match), and `isModelBenchmarkResultUsable()`/`filterUsableModelBenchmarkResults()` combining both. `MODEL_BENCHMARK_DEFAULT_TTL_MS` (30 days) mirrors the spirit of `model-router`'s own `OBSERVATION_MAX_AGE_MS` without importing it — device drivers, browser updates, and thermal/background conditions all drift over weeks even when nothing about the model/registry/runtime itself changed.
- `evidence.ts`'s `summarizeModelBenchmarkEvidence()` is the minimal pure aggregation contract a future router-integration phase will consume, given an already-filtered (compatible, non-expired, single-model) list of results: sample count, the most recent timestamp, median load/first-token/throughput (throughput aggregated only from `"exact"`-confidence samples), stable/neutral/negative run counts (reusing `classifyModelBenchmarkStability()` so neutral outcomes never inflate a failure count), and a count-gated `evidenceLevel` (`"none" | "weak" | "moderate" | "strong"`, via `MODEL_BENCHMARK_EVIDENCE_THRESHOLDS`). This function decides no router scoring weight — it exists so "one run must never dominate long-term stability observations" (see "Router relationship" below) is a testable property now, before any router wiring exists: a single sample is always `"weak"`, by construction, never anything stronger.

No new inter-package dependency edge affects `model-router`, `ai-runtime`, or `model-registry` in this phase: `@free-ai-open/model-benchmark` depends only on `@free-ai-open/types`, matching the same "shared contract in a zero-dependency leaf package" pattern the v0.7.0-alpha "Contract types and where they live" section above already established.

### Router relationship (defined, not wired)

Phase 0 defines the relationship only — `routeAdaptiveModel()` does not read `ModelBenchmarkResult` yet. When a future phase wires this in, the same rules the v0.7.0-alpha router already applies to `ModelPerformanceObservation`/`LocalBenchmarkResult` must hold: benchmark evidence is ADDITIONAL evidence, never a replacement for real usage observations, and must never instantly override a hard eligibility gate; one run must never dominate long-term stability observations built from many real generations (`evidence.ts`'s `summarizeModelBenchmarkEvidence()` above makes this a testable property today, ahead of any actual router-scoring weight); and a stale or incompatible result (per `isModelBenchmarkResultUsable()` above) is ignored outright, never merely down-weighted.

### Privacy model

- Benchmark runs happen entirely locally, in the browser — no accounts, no server inference, no remote benchmark upload.
- `ModelBenchmarkResult` never persists the benchmark prompt, any generated response text, exact GPU identifiers, or any unique fingerprinting identifier — only bounded technical measurements (timings, counts, an outcome code) and the same coarse references already used elsewhere (`capabilityProfileKey`, `browserFamily`), never a raw adapter string or a full `StaticCapabilityProfile`.
- A future diagnostic-report integration may include a coarse benchmark summary (technical reason codes/metrics only), matching the existing `contentLogged: false` guarantee everywhere else in this codebase — not implemented in this phase.

### Phase 1: runtime-backed performance metrics

**Status: Phase 1 only.** Extends `@free-ai-open/ai-runtime` so every local generation can expose the most accurate performance measurements the installed WebLLM runtime actually supports — the raw ingredients a future benchmark-runner phase will translate into the Phase 0 `ModelBenchmarkResult` contract above. Does NOT implement the benchmark runner, the `/benchmarks` page, or router-scoring integration; nothing here changes visible chat behavior.

- **Installed WebLLM version verified directly, not assumed.** `@mlc-ai/web-llm` 0.2.84 (see `packages/ai-runtime/package.json`/`pnpm-lock.yaml`). Its `lib/openai_api_protocols/chat_completion.d.ts`/`types.d.ts` were read before any code was written (see `runtime.ts`'s own top-of-file note, which records the exact findings): `stream_options: {include_usage: true}` is fully supported (`ChatCompletionRequestUnsupportedFields` is an empty array in this version's compiled bundle), and setting it causes a dedicated trailer chunk — `choices: []`, a populated `usage: CompletionUsage` — to follow the normal stream end. Earlier content/finish_reason chunks carry `usage` absent/null; only that one trailer chunk ever carries the real payload, computed by WebLLM's own pipeline (`getCurRoundDecodingTotalTokens()`/`getCurRoundPrefillTotalTokens()`), never derived from characters/words/chunks. An aborted/interrupted/degenerate-output stream never reaches this trailer at all.
- **Exact token usage, captured and validated, never estimated.** `runtime.ts`'s `buildGenerationTokenUsage()` validates WebLLM's raw payload (finite non-negative integers for `completion_tokens`/`prompt_tokens`/`total_tokens`, and `total_tokens === prompt_tokens + completion_tokens`) before trusting any of it; a single malformed field degrades the WHOLE measurement to `tokenCountConfidence: "unavailable"`, mirroring `@free-ai-open/model-benchmark`'s own sanitizer philosophy. Once validated, `overallCompletionTokensPerSecond` is derived from `ai-runtime`'s OWN measured FULL inference wall-clock duration (`generationDurationMs`) — deliberately NEVER from WebLLM's own self-reported `usage.extra.decode_tokens_per_s`/`prefill_tokens_per_s` (a different internal clock that could otherwise diverge from this package's own duration by more than a later consistency check's tolerance, producing an internally-inconsistent record once fed into Phase 0's contract). It requires `generationDurationMs` strictly positive to ever report `"exact"` at all, mirroring `sanitizeModelBenchmarkResult()`'s own rule.
  - **This is deliberately NOT a decode-only rate.** `generationDurationMs` spans from immediately before the WebLLM completion request to the moment the complete stream — INCLUDING the usage trailer chunk — has been fully consumed, so it includes worker/request overhead, prefill, time to first token, decode, and stream delivery. The field is named `overallCompletionTokensPerSecond` (never `decodeTokensPerSecond`/`generationSpeed`) specifically so a future consumer (e.g. a Phase-2 benchmark runner) cannot mistake it for decode-only throughput.
  - **No prompt/prefill throughput is exposed.** WebLLM's own `usage.extra.prefill_tokens_per_s` is real, but this package does not promote it into the trusted contract, and `promptTokens / timeToFirstTokenMs` is NOT exact prefill throughput either — TTFT includes worker/message round-trip, request scheduling, and first-token sampling, not just prefill (see `timeToFirstTokenMs`'s own doc comment). Neither is trustworthy enough to sit inside an object whose own discriminant claims `"exact"`, so `GenerationTokenUsageExact` carries only `promptTokens`/`completionTokens`/`totalTokens` (exact counts) plus `overallCompletionTokensPerSecond` — no prompt-throughput field at all. TTFT itself is unchanged and must never be reinterpreted as a prefill-time measurement.
- **New package-local types, not imported from `@free-ai-open/types`.** `GenerationTokenUsageExact`/`GenerationTokenUsageUnavailable`/`GenerationTokenUsage` and `GenerationRuntimeMetrics` (inference-start/first-token/completion timestamps, TTFT, generation duration, and the usage above) live in `ai-runtime/src/types.ts`, deliberately NOT reusing `ModelBenchmarkGenerationMeasurement` — `ai-runtime` takes on no new dependency (not even on `@free-ai-open/types`) merely to reuse a type; a future benchmark-runner phase translates this shape into the Phase 0 contract, exactly as `apps/web` already translates raw `ai-runtime` chunks into `ModelPerformanceObservation` today (see "Measured-performance integration" above). `GenerationRuntimeMetrics` is attached directly to the terminal `{type: "done", ...}` `GenerateChunk` — a focused, per-attempt result, not a new generic analytics API — and is never aggregated across separate `generate()` calls: each Continue attempt gets its own independent object. `loadModel()` similarly now resolves to `ModelLoadRuntimeMetrics | null` (that call's own wall-clock duration; `null` on failure) instead of `void`.
- **TTFT measurement point unchanged.** Still measured from the exact same raw WebLLM stream chunk the v0.7.1 generation watchdog itself reads from (see "Streaming render responsiveness" and "Generation timeout and stall watchdog" above) — never from React rendering, buffered transcript flushes, or any downstream consumer. Usage capture adds one new independent check per chunk (`if (chunk.usage) ...`, since WebLLM's usage trailer has empty `choices` and would otherwise be silently skipped) without touching the watchdog's own progress/stall timers, cancellation state, or generation-epoch bookkeeping.
- **Model load time stays honestly scoped.** The installed WebLLM version exposes no structured download-vs-initialization split (`InitProgressReport.text` is a free-form string, not a phase enum), so `ModelLoadRuntimeMetrics.loadTimeMs` remains "however long this `loadModel()` call took" rather than a claimed "download time." An already-loaded, reused model still has no load measurement at all (Phase 0's own semantics), since `loadModel()` is simply not called again for it — a decision made above this package.
- **Local technical logs extended, not overclaimed.** `@free-ai-open/local-logs`'s `LocalLogPerformanceMetrics` gained `tokenCountConfidence`/`exactGeneratedTokenCount`/`exactPromptTokenCount`/`exactOverallCompletionTokensPerSecond`, each independently validated in `sanitize.ts` and dropped (never coerced) when malformed, kept entirely separate from the pre-existing heuristic, chunk-count-derived `tokensPerSecond` field. There is no `exactPromptTokensPerSecond`-style field: prompt throughput is never logged as exact, for the same reason it is never exposed on `GenerationTokenUsageExact`. No new network call, no telemetry upload; `contentLogged` stays `false`.
- **Dependency boundary unchanged.** `ai-runtime`'s `package.json` gained no new dependency; `apps/web/app/_lib/packageDependencyBoundaries.test.ts`'s existing v0.7 assertions (`ai-runtime` must not depend on `model-router`/`model-registry`) remain the relevant coverage — this phase adds no edge for them to catch.
